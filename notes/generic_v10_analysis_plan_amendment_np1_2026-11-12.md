## NP1.2 Cells, scope and order
- **The cells (D135):** three replicates each for CHORUS, CM4AI, VOICE and AI_READI, and one each for VOICE_PEDIATRIC and Kids First if in scope. Records go under `claudecode_direct{,_core}/<label>/` (D27; N1.1).
- **A cell** is (arm, project, replicate position), as plan §3 defines it (lines 715–718). Each registration declares the position it fills. This amendment uses "cell" only in that sense. The whole native arm under the shared-v1 protocol is called **the native shared-v1 condition**.
- **A production cell** [proposed, NP1.10(d)] is any cell of this amendment that is not a pilot: the twelve replicate cells and the two descriptive cells. Every one of them that is in scope (thirteen for the study's five projects, and a fourteenth if Kids First passes the inputs test) runs under the registered floor and under NP1.6's acceptance rows, attempt bound, classification and stop-loss. Only the twelve replicate cells can enter a verdict.
- **The N1 canary is never one of these cells** (D25, D107; N1.5), and neither is a pilot.
- **Scope rule** [proposed, NP1.10(a)]: the plan's rule (lines 333–355), narrowed for the native arm.
  - **Whole projects only.** A project is in or out with all its cells. Replicates are never trimmed inside a project.
  - **The order** is the plan's (lines 340–344): CHORUS ×3 → CM4AI ×3 → VOICE ×3 → AI_READI (pilot + ×3) → VOICE_PEDIATRIC ×1 → Kids First ×1. Under NP1.7 every pilot runs before the floor is registered and so before any production cell, as the plan's own pilot does (lines 307–312).
  - **Scope is decided at NP1b, by one test of inputs.** A project is in scope if all three hold at the merged source NP1b runs on: (1) the project's source manifest, named below, declares it, with a bundle and a chunk manifest; (2) the repository's own checks, run with that manifest, report that bundle and chunk manifest current (`d4d download audit-bundles` and `d4d bundle chunk --check`); (3) the production prepare and validate functions accept the first part of a registration for it, built from its real inputs: the receipt policy, the selection, the schema, prompt and profile pins and the byte inventory, with selection bounds inside the ceilings the source fixes and the runtime terms NP1.7 registers for it. NP1b records the commands, their saved outputs and each project's result, and both reviewers check them. If the production source pinned at the floor's registration is another commit, that document repeats the test on it (NP1.5).
  - **Which manifest the test reads, fixed here.** For CHORUS, CM4AI, VOICE, AI_READI and VOICE_PEDIATRIC: the study's source manifest, `data/preprocessed/source_manifest.yaml`. For Kids First: the tracked manifest `notes/matched_cborg_2026-09-13/kids_first/manifest.yaml`, whose sha256 at main `7ad8c9e7295f1575ae9108ea62c12c83b1dd4db1` is `aa00b62d689aa33d4d6c15d106e620321b295563b14401536e4dc77430d045fd`. No other manifest is read for this test. NP1b records the sha256 of each manifest it read; if Kids First's differs from that value, the difference is recorded with its reason.
  - **What the test does not limit.** It tests that a project's inputs exist and are well formed. It applies no size limit below the source's own ceilings, and it does not test whether a larger project completes inside its registered runtime terms. Only a run shows that (NP1.7).
  - **Where the inputs stand.** Per the lead's record, a helper ran this test offline on 2026-11-12 on the unmerged candidate source, with the study's manifest: CHORUS, CM4AI, VOICE, AI_READI and VOICE_PEDIATRIC passed. **Kids First's test has not been run.** What exists for it, read by the lead at main `7ad8c9e7295f1575ae9108ea62c12c83b1dd4db1`: the plan records its bundle at 541,184 bytes (lines 658 and 1929); a file of that size is tracked at `notes/matched_cborg_2026-09-13/kids_first/KIDS_FIRST_preprocessed.txt`; the manifest beside it is a version-1 source manifest that declares `profile: neutral` and the project `KIDS_FIRST` with that bundle; `chunks.yaml` beside it records `bundle_bytes: 541184` and 58 chunks; and an omission context is tracked at `data/omission_contexts/kids_first_omission_context.json`. The study's own manifest declares no Kids First project, and `data/preprocessed/` holds no Kids First bundle. v6 said that no source manifest declared Kids First. That was wrong: the Claude review of v6 found the tracked manifest. Whether Kids First passes parts (2) and (3) is not known until the test is run on that manifest, and NP1b's run decides.

    - **Stopping at receipt completion instead** would change how attempts are stopped. That is a change of scientific procedure and a new stratum, under its own prospective amendment (NP1.7).
  - **The alternative that was offered, and not taken (D140):** the floor measured on the final record, as the code has it today, with only the #5939 sentence of the asset changed. Its consequences are kept here as the record of what was offered:

> The registered native coverage floor is the lowest of the eligible native pilots' D37 at-receipt coverage fractions, `with_receipt_at_receipt / receiptable_at_receipt`, rounded down to a multiple of 1/20 and capped at 19/20.

  - **Had NP1.10(r) been answered no,** the rule would have read `with_receipt / receiptable` on the final record. It was answered at-receipt (D140), so the rule reads as written.

Only an accepted attempt's saved result supplies a fraction; a rejected, stopped or assisted attempt never does (lines 1129–1133).

  - **The second reading is a check, never an input.** On the at-receipt basis the receipt-completion stage's `after` block is the checker run on the sealed original with the completed receipt (`:433–437`), so it should equal the final-stage pair. It is reported beside it. If the two differ, that is an instrument defect: it is filed as a finding, and the floor is not registered while it is unresolved. The floor's registration never chooses between two observed ratios. **The check applies on the at-receipt basis only.** On the final-record basis the two readings differ by design: the completion stage's `after` block reads the phase-1 record, and the gated ratio reads the final record.

It does not enter the rule and does not gate a production record. Final-record coverage is reported for every record as the plan's descriptive quantity.

  - **An accepted pilot whose saved result has no such reading** supplies no fraction. Its project stays in scope, and the floor is not registered (below).
  - **Arithmetic:** exact integers, `floor(20 × with_receipt_at_receipt / receiptable_at_receipt) / 20`, then the minimum with 19/20, registered as a numerator over the denominator 20.
  - **Why the cap:** the plan's reason (lines 1134–1140). Receipt completion drives the at-receipt ratio towards 1, and a floor of 1 would stop a replicate on one unreceipted leaf.
  - **The lowest value that can be registered is 1/20.** The plan's rule rests on a re-canary that has passed its own 19/20 gate (lines 1147–1149). The native canary is ungated (D109), so the native floor is wholly the pilots' own reading. A low reading registers a low floor, which gates little. The value is reported with that said, and every production record's coverage is reported whatever the floor. A reading under 1/20 cannot be registered: the pilot's project stays in scope, and the floor is not registered (below).
  - **The AI_READI branch.** NP1.6's table says how the pilot concludes. While it is pending the floor waits (below). If it concludes without acceptance for a cause that is not rule-level, AI_READI leaves scope as infeasible, reported as a feasibility result, and CHORUS's pilot alone sets the value (plan step 8, lines 307–312). A rule-level rejection is NP1.6's case. An accepted AI_READI pilot never takes AI_READI out of scope, whatever its reading.
  - **When the floor is not registered.** In each of these cases no production cell registers, and no other observed ratio is substituted (lines 1150–1152):
    - **a required pilot is still pending,** or waits on an instrument or unknown case (NP1.6): the floor waits for it;
    - **on the at-receipt basis, an instrument finding on the two readings is open:** the floor waits until it is resolved;
    - **an accepted pilot has no usable fraction:** its saved result has no final-stage reading, its denominator is zero, or its reading is under 1/20. Its project stays in scope. A prospective amendment, reviewed as this one, says how the floor is set;
    - **CHORUS has no pilot fraction,** because its pilot or its re-run concluded without acceptance (NP1.6), or because a second re-run would be needed (above): a prospective amendment says how the stratum proceeds.

    An AI_READI pilot that concludes without acceptance for a cause that is not rule-level is not one of these cases: AI_READI leaves scope, and CHORUS's pilot alone sets the value.
  - **Conformance, not choice.** The floor's registration confirms from the merged source that these are still the fields. If the merged source differs, the floor is not registered until a prospective amendment restates it.
