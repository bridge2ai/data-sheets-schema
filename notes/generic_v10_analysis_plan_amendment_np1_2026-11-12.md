- **The gate** [proposed, part of NP1.10(al)]: a comparison of the registrations' pins and declared values, not a replay (the lead's decision, Authority). It is a script with a data file. **The data file is a closed field-level schema:** it classifies every field a registration packet records into one of three kinds, under the principle below. Both are an engineering prerequisite, due before the canary's registration, assigned and not written (NP1.7).
  - **What runs** (the lead's ruling, Authority). No code from either tree is run to produce what the model reads; that would be a replay. The gate validates both packets with the existing production validators, read-only, in an isolated process, from the reference run's own source export, never from the candidate's tree. The candidate's code is never executed: where its pinned files equal the reference's, the validators are the same code; where they do not, the result is "not equal" from the pins alone (below). The comparison of fields then reads data only.
  - **The principle.**
    1. **Identical:** every value that can change what runs, what the model reads or how acceptance is decided. Among them: the pins of the package source and of every other pinned file, the prompt assets, the `.claude` command and agent files, the schema closure, the closed dependency registry, the Claude Code binary's sha256, the base system-instructions bytes, the interpreter's version, the environment manifest of the third-party distributions and the interpreter's identity, the selection bounds (NP1.10(ap)), the run limits and every other runtime value, the values the observation probe records about the model and its limits, and every scientific registered value. A value that decides what runs is identical even where it is written as a path, such as the executable search path.
    2. **Per-run:** a value that only names or locates this run. Among them: identifiers (registration, selection, job, attempt and session), labels, the run's project, timestamps and validity dates, the paths of the run's separate attempt, evidence, output and stage roots, of its configuration directory and of its registration, composition, instruction, runtime-declaration and probe files, the capture-state directory, the device and inode numbers that fingerprints record, and the checkout and interpreter paths. The project-input fields are per-run only as far as the rule on a project's inputs allows (below).
    3. **Derived:** a value that pinned code computes from the fields above. Among them: the embedded preparation and composition documents, the command line and the environment, the command guidance appended to the system prompt, the selection, preparation, composition, policy, instruction, probe and expectation hashes, and the byte counts recorded beside them. The gate recomputes each from the candidate's own content and requires it to validate. A derived value is never merely exempted.
  - **Every recorded field is classified.** A field the schema does not classify is "cannot decide" (below). The data file names each field by its location in the registration packet that the merged source builds, and both reviewers check it against that source.
  - **A project's inputs** must equal that project's input tuple pinned at NP1b, exactly: the study's source manifest as one whole file, and the project's bundle, chunk manifest, omission context and scope declaration, each by sha256 (NP1.2). The reference's tuple is CHORUS's. A change to a tuple needs a prospective amendment; until one is ratified, a registration with other inputs is not equal.
  - **The floor's change** is the one permitted change of an identical value, and it is checked separately. A pilot's receipt-policy registration carries `{state: pending, mode: diagnostic_pilot}`; a production cell's carries the registered fraction. The gate requires that the production cell's value and basis (`receipted_part`) are exactly those of the floor's ratified registration (NP1.7 step 6), computed by NP1.10(s)'s arithmetic, and that every other field of the receipt-policy registration is identical. The hashes that carry it are derived values and are recomputed. What that one value does inside a run, where helper output shows "pending" in a pilot and "passed" in production, is the pinned code acting on that value. It is never compared, because no run is executed.
  - **The comparison-input manifest.** Before it compares anything, the gate writes an immutable manifest that names its inputs by path and sha256: the reference's registration packet and the candidate's, each as the registration builder wrote it, before any gate result or review is added; the floor's registration, where it applies; the project's input tuple; and the gate's script and data file. The manifest's sha256 covers the manifest file's bytes. The gate's result names that sha256, and the result and the registration's two reviews go in an outer evidence packet that refers to these hashes. No hash covers a file that refers back to it.
  - **Three results, disjoint.**
    - **Equal:** both packets pass the production validators, every field is classified, every identical field is byte-identical, every derived field validates, the inputs equal the project's tuple, and the floor's change, where present, checks.
    - **Not equal:** valid evidence of a prohibited difference. A pinned file whose recorded sha256 differs from the reference's decides it from the pins alone, before any validation of the candidate; a packet that cannot be read that far is "cannot decide". Otherwise both packets are validated, every field is classified, and the evidence shows an identical field that differs, a project-input field that does not match the tuple, a floor value or basis other than the floor's ratified registration, or bounds other than the stratum's. Every differing field is listed. The registration is not in this stratum.
    - **Cannot decide:** the evidence is invalid or incomplete: a packet fails the production validators, a pinned file is missing, a field is not classified, or a derived value cannot be recomputed. It is a hold: that registration is not made until the cause is repaired. It is never a pass and never a reason for another pilot.

- **The rule** [proposed, NP1.10(s)]. It is the plan's floor rule (§8, lines 1125–1127) read for native pilots, and it takes no value from the API arm:

> The registered native coverage floor is the lowest of the eligible native pilots' D37 at-receipt coverage fractions, `with_receipt_at_receipt / receiptable_at_receipt`, rounded down to a multiple of 1/20 and capped at 19/20.

  - **Eligible pilots:** the reference run, which is the first accepted attempt of the CHORUS reference pilot (above), and, if NP1.10(e) is yes and AI_READI is in scope, the AI_READI native pilot. **The canary's reading is reported and is never an input;** that supersedes D109's clause quoted above.   - **Which reading: one.** Each pilot contributes one fraction, from the `slots` of its final-stage receipt check: the block the controller writes with `native_receipt_stage: final` (`native_shared_receipts.py:484–498`), read from the accepted attempt's saved result.
  - **The second reading is a check, never an input.** On the at-receipt basis the receipt-completion stage's `after` block is the checker run on the sealed original with the completed receipt (`:433–437`), so it should equal the final-stage pair. It is reported beside it. If the two differ, that is an instrument defect: it is filed as a finding, and the floor is not registered while it is unresolved. The floor's registration never chooses between two observed ratios. **The check applies on the at-receipt basis only.** On the final-record basis the two readings differ by design: the completion stage's `after` block reads the phase-1 record, and the gated ratio reads the final record.

  - **What gates in production:** the final-stage check's reading on the chosen basis, against the registered fraction (above, and NP1.6).
  - **An accepted pilot whose saved result has no such reading** supplies no fraction. Its project stays in scope, and the floor is not registered (below).
  - **Arithmetic:** exact integers, `floor(20 × with_receipt_at_receipt / receiptable_at_receipt) / 20`, then the minimum with 19/20, registered as a numerator over the denominator 20.

  - **The lowest value that can be registered is 1/20.** The plan's rule rests on a re-canary that has passed its own 19/20 gate (lines 1147–1149). The native canary is ungated (D109), so the native floor is wholly the pilots' own reading. A low reading registers a low floor, which gates little. The value is reported with that said, and every production record's coverage is reported whatever the floor. A reading under 1/20 cannot be registered: the pilot's project stays in scope, and the floor is not registered (below).
  - **The AI_READI branch.** NP1.6's table says how the pilot concludes. While it is pending the floor waits (below). If it concludes without acceptance for a cause that is not rule-level, AI_READI leaves scope as infeasible, reported as a feasibility result, and the CHORUS reference run alone sets the value (plan step 8, lines 307–312). A rule-level rejection is NP1.6's case. An accepted AI_READI pilot never takes AI_READI out of scope, whatever its reading.
  - **When the floor is not registered.** In each of these cases no production cell registers, and no other observed ratio is substituted (lines 1150–1152):
    - **a required pilot is still pending,** or waits on an instrument or unknown case (NP1.6): the floor waits for it;
    - **an instrument finding on the two readings is open:** the floor waits until it is resolved;
    - **an accepted pilot has no usable fraction:** its saved result has no final-stage reading, its denominator is zero, or its reading is under 1/20. Its project stays in scope. A prospective amendment, reviewed as this one, says how the floor is set; it is under the bar, which says what it may apply (above);
    - **there is no reference run,** because the CHORUS reference pilot concluded without acceptance (NP1.6): a prospective amendment says how the condition proceeds;

    An AI_READI pilot that concludes without acceptance for a cause that is not rule-level is not one of these cases: AI_READI leaves scope, and the CHORUS reference run alone sets the value.
  - **Conformance, not choice.** The floor's registration confirms from the reference run's source that these are still the fields. If they are not, the floor is not registered until a prospective amendment restates it.
