## NP1.2 Cells, scope and order
- **The cells (D135):** three replicates each for CHORUS, CM4AI, VOICE and AI_READI, and one each for VOICE_PEDIATRIC and Kids First if in scope. NP1.10(c) proposes that Kids First is not planned under this amendment (below). Records go under `claudecode_direct{,_core}/<label>/` (D27; N1.1).
- **A cell** is (arm, project, replicate position), as plan §3 defines it (lines 715–718). Each registration declares the position it fills. This amendment uses "cell" only in that sense. The whole native arm under the shared-v1 protocol is called **the native shared-v1 condition**.
- **A production cell** [proposed, NP1.10(d)] is any cell of this amendment that is not a pilot: the twelve replicate cells and VOICE_PEDIATRIC's descriptive cell. Every one of them that is in scope, thirteen for the study's five projects, runs under the registered floor and under NP1.6's acceptance rows, attempt bound, classification and stop-loss. Only the twelve replicate cells can enter a verdict.
- **The N1 canary is never one of these cells** (D25, D107; N1.5), and neither is a pilot.
- **Scope rule** [proposed, NP1.10(a)]: the plan's rule (lines 333–355), narrowed for the native arm.
  - **Whole projects only.** A project is in or out with all its cells. Replicates are never trimmed inside a project.
  - **The order** is the plan's (lines 340–344): CHORUS ×3 → CM4AI ×3 → VOICE ×3 → AI_READI (pilot + ×3) → VOICE_PEDIATRIC ×1. The plan's order ends with Kids First ×1, which this amendment does not plan (below). Under NP1.7 every pilot runs before the floor is registered and so before any production cell, as the plan's own pilot does (lines 307–312).
  - **Scope is decided at NP1b, by one test of inputs.** A project is in scope if all three hold at the merged source NP1b runs on: (1) the project's source manifest, named below, declares it, with a bundle and a chunk manifest; (2) the repository's own checks, run with that manifest, report that bundle and chunk manifest current (`d4d download audit-bundles` and `d4d bundle chunk --check`); (3) the production prepare and validate functions accept the first part of a registration for it, built from its real inputs: the receipt policy, the selection, the schema, prompt and profile pins and the byte inventory, with selection bounds set by the reference's rule (NP1.5) and the production limit set (NP1.7). NP1b records the commands, their saved outputs and each project's result, and both reviewers check them. NP1b runs the test on the reference run's source where that run has been accepted, and otherwise on the merged source on which the CHORUS reference pilot registers (NP1.7).
  - **Which manifest the test reads, fixed here:** the study's source manifest, `data/preprocessed/source_manifest.yaml`, for all five projects. No other manifest is read for this test. NP1b records the sha256 of the manifest it read.
  - **What the test does not limit.** It tests that a project's inputs exist and are well formed. It applies no size limit below the source's own ceilings, and it does not test whether a larger project completes inside its registered runtime terms. Only a run shows that (NP1.7).
  - **Where the inputs stand.** Per the lead's record, a helper ran this test offline on 2026-11-12 on the unmerged candidate source, with the study's manifest: CHORUS, CM4AI, VOICE, AI_READI and VOICE_PEDIATRIC passed. NP1b's run decides.
  - **A project that fails the test is out of scope, labelled "not planned (NP1b: inputs)".** It has no cells. That is different from missing: it is not counted in K_native (NP1.3), and plan §7's missing-cell rules apply only to in-scope cells (lines 347–349). Inputs added after NP1b do not bring a project in; that needs a prospective amendment.
  - **No usage reading and no quality value decides scope at NP1b.** The plan funds the longest prefix of the order that a dollar budget covers (lines 345–346). The native arm has no such budget, and this amendment sets none: no number of weeks and no estimate of attempts per week. Each attempt is admitted by the guard's terms at its own launch (NP1.7) and needs its own word. (D22, quoted under Authority). The owner paces or ends the batch by giving or not giving words.
  - **AI_READI can also leave scope at its pilot,** reported "out of scope (pilot)", and only when the pilot concludes without acceptance by NP1.6's table, a rule fixed here. A withheld word concludes nothing and removes nothing, and an accepted pilot with no usable fraction removes nothing either (NP1.5, NP1.6).
  - **After K_native is fixed (NP1.3), nothing removes a project from scope.** What happens to its cells is described with the plan's three kinds of missing (lines 777–781). A cell whose attempts end without acceptance is acceptance-missing, and its attempts' eligible records still enter Set A (lines 1094–1104). A cell with no eligible full record is artifact-missing; a cell that never had an attempt, because no word was given, is both. A project has a primary verdict only with complete n=3 on each side under definition (2) and with every snapshot and block the metric requires, measured (lines 844–853); otherwise it counts as "not measured" in "k of K_native".

Every pilot runs with a pending floor, so none could have been accepted. Its repair is a prerequisite of any pilot (NP1.7 gives its state), and the rule the code has to match is amendment N1's: N1.4(B) rows 0 and 5.
  - **What the repair is.** N1.4(A) item 5 quotes "A pending scientific receipt floor cannot become strict success." The repair keeps that: the structural receipt floors still gate the final strict check and the receipts gate, and under a pending registration the coverage floor is reported as UNMEASURABLE and never as a pass. The owner chose its replacement on 2026-11-12 (D142, quoted under Authority). - **What a registered native floor is in the code.** Two identities are involved:
  - **the policy asset,** `native_shared_receipt_policy_v1.md`, a model-facing file selected and pinned by sha256;
  - **the receipt-policy registration,** a separate JSON document that names the asset by `runtime_policy_sha256` and carries `coverage_floor`, which is either `{state: pending, mode: diagnostic_pilot}` or `{state: registered, numerator, denominator}` (`native_shared_contract.py:785–810`).

  Registering a value makes new registration bytes with a new sha256, which each production registration selects. The policy asset does not change at that step.
- **What the model is shown does change.** The initial receipt check's output carries the registration's JSON (`native_shared_receipts.py:369–374`), and the receipt-stage request carries the parsed policy (`:389–391`). So a production run's model sees the registered fraction from phase 1 on, where a pilot's model sees `pending`.
  - **This is the planned difference between a pilot and a production cell,** beyond its inputs (NP1.7). The stage-request hashes on both sides are retained, so the difference is shown and not inferred.
  - **What it means for comparing a pilot with production.** A pilot's coverage is produced with no target in view. Production coverage is produced with one. The floor is a threshold taken from the first kind of reading and applied to the second. Whether a visible target raises coverage, or leads a model to leave out, before the seal, values it cannot receipt, is not known. Production's populated-leaf counts (prediction 1) and coverage (prediction 2) are read with that. Pilot readings are never pooled with production readings and never set beside them as like for like.
- **The basis** [answered: at-receipt, NP1.10(r); D140]: **the native floor is measured on D37's at-receipt basis,** as the plan's floor is and as the API arm's registration is (`basis: receipted_part`). The owner decided on 2026-11-12: "The native production floor is measured on the at-receipt basis of D37." (D140).
  - **What the plan and D37 say.** "D37 fixes the snapshot basis" (line 1117). The plan's rule reads "D37 at-receipt coverage fractions, `with_receipt_at_receipt / receiptable_at_receipt`" (lines 1125–1127) from the accepted attempt's frozen `O,R1` snapshot (line 1131). The plan calls final-record coverage descriptive (§3a, lines 880–881), and says "deleting unreceipted leaves **does not improve source coverage**" (lines 893–894).

  - **If the answer to this item is no,** the consequence is fixed and nothing is redrafted: the canary's reading is not a floor input, the canary is not the reference run, and the CHORUS reference pilot is run.

- **No change may rest on a native result** [proposed, NP1.10(ao)]. The plan says of P4b: "It may not use any v10 quality value, A21's included, to choose a project or a threshold. - **The reference run** [proposed, NP1.10(al)]. One rule, with no pilot run again and no production source chosen. It replaces v7's pinned source, its two-part test and its re-run pilots.
  - **What it is.** The production stratum has one reference: **the first accepted CHORUS pilot attempt that ran under the production limit set and whose first coded word followed this amendment's ratification** (NP1.10(ab), NP1.10(aj)).
    - **Under one limit set** (alternative A of NP1.10(ab)) that is the N1 canary, if it is accepted and NP1.10(aj)'s condition held.
    - **Under two limit sets** (alternative B, the owner's recorded answer, D143), or where NP1.10(aj)'s condition failed, it is the first accepted attempt of **the CHORUS reference pilot** (NP1.6): one CHORUS pilot registered after NP1b, under the production limit set, with the floor pending.

  - **What the reference fixes.** Everything that run's registration pinned: its source commit, its selected prompt assets and schema closure, its registered values, and three things the model reads that are set per registration: **the Claude Code binary** (by sha256), **the system prompt** (the system-instructions file and the command guidance, by sha256) and **the rule by which its selection bounds are set.** Each of those three is pinned by the registration, and each is the same for every run of this stratum (`native_shared_registration.py:46`, `:247–256`; `native_shared_contract.py:109–122`, `:662–670`: audit, from the Claude review of v7).
  - **Every later registration is equal to the reference, or it is not in this stratum.** The AI_READI pilot's registration and every production cell's registration are compared with the reference by the comparison below. **Equal:** the registration belongs to this stratum. **Not equal:** it does not, and it is not made under this amendment. Nobody chooses a production commit, and nobody decides whether a difference matters.
  - **Two things differ between a run and the reference, and each is declared.** A project's inputs: the comparison is run on the reference's saved inputs, so they do not enter it. And the coverage floor in the receipt-policy registration, which is pending in a pilot and the registered fraction in a production cell (above, on what the model is shown); the comparison's data file names that one field.
  - **No pilot is run again.** A pilot's reading is never replaced by a second run of that pilot. A change that the comparison finds not equal **ends this stratum for the runs registered after it.** Those runs need a new prospective amendment, which names its own pilots before any of them runs and is bound by the bar above. This stratum's floor, its K_native and its readings never move, and a reading that a later stratum does not use is still reported. A change that the comparison finds equal stays in this stratum, on D35's terms (NP1.7).
  - **What this costs.** After the reference run, a repair that changes anything the model reads, or any rule-bearing object, cannot be taken into this stratum, however small. That includes an update of the binary or of the system prompt. The remedy is a new amendment with its own pilots, not a judgment that the change is harmless.
- **The comparison** [proposed, part of NP1.10(al)]. It is a script with a data file. Both are pinned by sha256 in the reference run's registration packet, so both exist before that registration: **an engineering prerequisite, assigned and not written** (NP1.7). This amendment fixes what it does.
  - **What it compares, between a registration and the reference, on the reference's saved inputs:**
    1. **what the model reads:** the complete rendered instruction; every stage request of one fixed sequence; the system prompt and the tool policy as the binary receives them; the selected prompt assets; the schema closure; and the output that helpers return to the model on those inputs, the initial receipt check's among them (`native_shared_receipts.py:369–374`);
    2. **the rule-bearing source objects:** the gates, the floors and their thresholds, the receipt predicates, the attempt accounting, the cause classification, and the registered limits and admission terms. The data file lists them by name.
  - **Permitted differences are exact locations, listed in the data file, and of identity kinds only:** a hash, an identifier, a timestamp in one named format, a path under the attempt directory. A hash that depends on a permitted difference is recomputed from the normalized content on both sides and must then agree; it is never ignored. Nothing is normalized by pattern. Numeric settings are content.
  - **The run limits are content.** With the four protected files the owner approved (D139), the instruction's recorder command carries `--render-spec-json`, whose value embeds the raw runtime declaration, and that declaration contains `deadline_seconds` and `budget_guard_usd` (`api_runner.py:1194–1210`; `native_shared_render.py:185–214`, `:289–295`, `:378–380`; `native_shared_runtime_constants.py:8–9`; read by the lead at `6561dac3c3af50cbfce1ba3c8b6ad21d9cd4b834`). So two runs under different limit sets read different instructions. v7 said the model reads neither limit; both reviews of v7 found that wrong. At the earlier cited commit, without those four files, the instruction does not carry the declaration, which is what the Claude review read; the script's output on the reference's source settles it.
  - **What it does not compare.** The permission expectation embeds the sha256 of every production source module and the whole runtime declaration (`native_shared_registration.py:141–182`, audit, from the Claude review of v7). The model does not read it, and comparing it would make every source change "not equal". The comparison takes the tool policy the binary enforces, not those hashes.
  - **Three results.** **Equal.** **Not equal,** with every difference listed by location. **Cannot decide:** an artifact could not be produced, an object on the list is missing on one side, or a difference sits at a location the data file does not cover. "Cannot decide" is a hold: the registration waits until the cause is repaired and the comparison is run again. It is never a pass, and it is never a reason for another pilot. **Any difference in a rule-bearing object is "not equal",** and no reviewer judges whether it matters: v7's second part, a written comparison that two reviewers confirmed after the readings were known, is removed.
  - **What the reviewers do.** The two reviewers of a registration confirm that the script and the data file are the pinned ones, that they were run on the reference's saved inputs and on this registration, and that the saved result is the one in the packet. They do not interpret it. The comparison shows that what a run was given, and the rules it is judged by, are the reference's. It cannot show that the provider's model is the same from run to run; the plan declares that drift (lines 959–961).
- **The rule** [proposed, NP1.10(s)]. It is the plan's floor rule (§8, lines 1125–1127) read for native pilots, and it takes no value from the API arm:

> The registered native coverage floor is the lowest of the eligible native pilots' D37 at-receipt coverage fractions, `with_receipt_at_receipt / receiptable_at_receipt`, rounded down to a multiple of 1/20 and capped at 19/20.

  - **Eligible pilots:** the CHORUS reference run and, if NP1.10(e) is yes and AI_READI is in scope, the AI_READI native pilot. **The CHORUS reference run** is the N1 canary under one limit set where NP1.10(aj)'s condition held, and otherwise the first accepted attempt of the CHORUS reference pilot (above). Where the canary is not the reference, its reading is reported and is never an input. Only an accepted attempt's saved result supplies a fraction; a rejected, stopped or assisted attempt never does (lines 1129–1133).
  - **Which reading: one.** Each pilot contributes one fraction, from the `slots` of its final-stage receipt check: the block the controller writes with `native_receipt_stage: final` (`native_shared_receipts.py:484–498`), read from the accepted attempt's saved result.
  - **The second reading is a check, never an input.** On the at-receipt basis the receipt-completion stage's `after` block is the checker run on the sealed original with the completed receipt (`:433–437`), so it should equal the final-stage pair. It is reported beside it. If the two differ, that is an instrument defect: it is filed as a finding, and the floor is not registered while it is unresolved. The floor's registration never chooses between two observed ratios. **The check applies on the at-receipt basis only.** On the final-record basis the two readings differ by design: the completion stage's `after` block reads the phase-1 record, and the gated ratio reads the final record.
  - **Readings that are not used.** The controller also evaluates the floor at the initial receipt check, where it forces the state to pending (`:363–364`). That is reported. It does not enter the rule and does not gate a production record. Final-record coverage is reported for every record as the plan's descriptive quantity.
  - **What gates in production:** the final-stage check's reading on the chosen basis, against the registered fraction (above, and NP1.6).
  - **An accepted pilot whose saved result has no such reading** supplies no fraction. Its project stays in scope, and the floor is not registered (below).
  - **Arithmetic:** exact integers, `floor(20 × with_receipt_at_receipt / receiptable_at_receipt) / 20`, then the minimum with 19/20, registered as a numerator over the denominator 20.
  - **Why the cap:** the plan's reason (lines 1134–1140). Receipt completion drives the at-receipt ratio towards 1, and a floor of 1 would stop a replicate on one unreceipted leaf.
  - **The lowest value that can be registered is 1/20.** The plan's rule rests on a re-canary that has passed its own 19/20 gate (lines 1147–1149). The native canary is ungated (D109), so the native floor is wholly the pilots' own reading. A low reading registers a low floor, which gates little. The value is reported with that said, and every production record's coverage is reported whatever the floor. A reading under 1/20 cannot be registered: the pilot's project stays in scope, and the floor is not registered (below).
  - **The AI_READI branch.** NP1.6's table says how the pilot concludes. While it is pending the floor waits (below). If it concludes without acceptance for a cause that is not rule-level, AI_READI leaves scope as infeasible, reported as a feasibility result, and the CHORUS reference run alone sets the value (plan step 8, lines 307–312). A rule-level rejection is NP1.6's case. An accepted AI_READI pilot never takes AI_READI out of scope, whatever its reading.
  - **When the floor is not registered.** In each of these cases no production cell registers, and no other observed ratio is substituted (lines 1150–1152):
    - **a required pilot is still pending,** or waits on an instrument or unknown case (NP1.6): the floor waits for it;
    - **an instrument finding on the two readings is open:** the floor waits until it is resolved;
    - **an accepted pilot has no usable fraction:** its saved result has no final-stage reading, its denominator is zero, or its reading is under 1/20. Its project stays in scope. A prospective amendment, reviewed as this one, says how the floor is set;
    - **there is no reference run,** because the canary cannot be it and the CHORUS reference pilot concluded without acceptance (NP1.6): a prospective amendment says how the condition proceeds;
    - **the comparison's result for a pilot's registration is "cannot decide":** that registration waits, and so does the floor.

    An AI_READI pilot that concludes without acceptance for a cause that is not rule-level is not one of these cases: AI_READI leaves scope, and the CHORUS reference run alone sets the value.
  - **Conformance, not choice.** The floor's registration confirms from the reference run's source that these are still the fields. If they are not, the floor is not registered until a prospective amendment restates it.
- **How the value is registered** [proposed, NP1.10(z)]: in a dated amendment that gets this amendment's review and the owner's ratification. It checks the arithmetic and the inputs and does not revisit the rule (lines 1159–1163).

## NP1.6 Acceptance, attempts and stops
- **Each attempt is judged by N1.4(B)'s rows B0–B7** [proposed, NP1.10(u)], as ratified, on the saved result after the attempt ends. N1 wrote those rows for the canary. Applying them to the AI_READI pilot, to the CHORUS reference pilot and to every production cell is this amendment's proposal.
  - **Row B0 for production.** N1 wrote B0 for a pending floor: "The receipts gate uses the structural floors only, so D109's pending floor doesn't block it." For a production cell B0 reads the receipts gate with the structural floors and the registered coverage floor.

  - **Where a registered floor is enforced.** Inside the run, by the final strict receipt check. After the run, at finalization, by the receipts gate (audit). So a production attempt with a floor failure, as NP1.5 defines it, does not reach the recorder, and row B0 fails with it. A failed check that a permitted correction and a passing check supersede is not a floor failure, and neither is an assessment that is unmeasurable or not applicable (NP1.5). A floor failure is classified by its cause, a content slip, not as a controller fault. The other cases are classified by the plan's precedence.
- **Blind source review (B6) is per record** (D36): a fresh Claude session and a Codex CLI pass, neither of which generated or operated the run, with the second blind reviewer's recall seed pinned to `original_full` before anyone reads the audit.
- **The owner signs each acceptance record** (D36). [proposed, NP1.10(v)] The record keeps every heading of plan §6 (lines 1026–1048), with these native entries. **Identities:** the registration sha256 and the artifact sha256s stay; the roster sha256 has no native counterpart and is recorded as not applicable; the native identities N1.6 lists are added. **Check rows:** N1.4(B)'s rows B0–B7, in place of the plan's item-5 rows. **Clean-run checks:** the checks N1.4(B) puts on the saved result, in place of the journal and override checks, which are the API runner's. **Cost:** the runtime's own cost estimate and the usage-window readings, in place of "at that day's prices". - **Attempts** [proposed, NP1.10(w)]:
  - **At most two attempts per native production cell,** counted across every label and registration, then the owner reviews. This is the plan's bound (§7, lines 1066–1069; D07), which D113 already applies to the canary.
  - **An attempt** is one launch that consumed its reservation. A capture is not an attempt, and a refusal before the reservation consumes none. A capture that is fresh at the reservation but stale at dispatch stops the attempt, and it counts (N1.5).
  - **Every attempt is retained,** stopped and rejected ones included (lines 1052–1056). A stopped or rejected attempt is never resumed or re-run under its label; any new attempt needs a new label, registration and word (N1.5; D56).

The class fixes the next action, and the next action is the plan's. The canary's endings are classed the same way for this amendment's purposes (below).
  - **The termination mechanism is recorded separately and never decides the class.** The mechanism is what ended the process: the registered deadline, the registered dollar guard, a usage stop, a manual stop, a helper's terminal refusal, or the runtime's own end. An attempt that ended on the deadline is rule-level if row 2 matches, a content slip if row 3 does, and budget or clock only if no earlier row matches. "A content defect outranks every operational class" (line 1361).
  - **The canary's classification, for this amendment.** N1.5 says "a **transport, budget or environment stop** (deadline, usage, dollar guard, host) is not a scientific rejection". That list names mechanisms, and amendment N1 has no precedence rule of its own. For this amendment's pilot table a canary attempt's ending is classed by the plan's precedence, as every other pilot's is: a sustained content defect outranks an operational stop, "whatever else stopped the run" (line 1351). Where the two differ, this amendment's reading decides what the canary means for production. A second canary attempt that N1 allows, even an accepted one, does not undo a rule-level rejection under this amendment (NP1.10(h)).

  - **"The final records" of a stopped attempt** are its eligible full record (NP1.4) and that record's core.   - **B6 reads every attempt that kept a record,** stopped or not, a canary attempt included, so that whether a stopped attempt is rule-level never depends on whether someone chose to look. **"Kept a record" means that the attempt's saved capture pins a full or core record;** with a yes to NP1.10(n) that is the incomplete capture's snapshot (NP1.4).
