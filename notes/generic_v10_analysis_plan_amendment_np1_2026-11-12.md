## NP1.2 Cells, scope and order
- **The cells (D135):** three replicates each for CHORUS, CM4AI, VOICE and AI_READI, and one each for VOICE_PEDIATRIC and Kids First if in scope. Records go under `claudecode_direct{,_core}/<label>/` (D27; N1.1).
- **A cell** is (arm, project, replicate position), as plan §3 defines it (lines 715–718). Each registration declares the position it fills. This amendment uses "cell" only in that sense. The whole native arm under the shared-v1 protocol is called **the native shared-v1 condition**.
- **A production cell** [proposed, NP1.10(d)] is any cell of this amendment that is not a pilot: the twelve replicate cells and the two descriptive cells. Every one of them that is in scope (thirteen as the inputs stand, because Kids First's cell is not planned) runs under the registered floor and under NP1.6's acceptance rows, attempt bound, classification and stop-loss. Only the twelve replicate cells can enter a verdict.
- **The N1 canary is never one of these cells** (D25, D107; N1.5), and neither is a pilot.
- **Scope rule** [proposed, NP1.10(a)]: the plan's rule (lines 333–355), narrowed for the native arm.
  - **Whole projects only.** A project is in or out with all its cells. Replicates are never trimmed inside a project.
  - **The order** is the plan's (lines 340–344): CHORUS ×3 → CM4AI ×3 → VOICE ×3 → AI_READI (pilot + ×3) → VOICE_PEDIATRIC ×1 → Kids First ×1. Under NP1.7 every pilot runs before the floor is registered and so before any production cell, as the plan's own pilot does (lines 307–312).
  - **Scope is decided at NP1b, by one test of inputs.** A project is in scope if all three hold at the merged source that the production registrations pin: (1) the source manifest declares it, with a bundle and a chunk manifest; (2) the repository's own checks report that bundle and chunk manifest current (`d4d download audit-bundles` and `d4d bundle chunk --check`); (3) the production prepare and validate functions accept the first part of a registration for it, built from its real inputs: the receipt policy, the selection, the schema, prompt and profile pins and the byte inventory, with selection bounds inside the ceilings the source fixes and the runtime terms NP1.7 registers for it. NP1b records the commands, their saved outputs and each project's result, and both reviewers check them.
  - **What the test does not limit.** It tests that a project's inputs exist and are well formed. It applies no size limit below the source's own ceilings, and it does not test whether a larger project completes inside its registered runtime terms. Only a run shows that (NP1.7).
  - **Where the inputs stand.** Per the lead's record, a helper ran this test offline on 2026-11-12 on the unmerged candidate source: CHORUS, CM4AI, VOICE, AI_READI and VOICE_PEDIATRIC passed. Kids First did not, because the source manifest declares no Kids First project. **What exists for Kids First,** read by the lead at main `7ad8c9e7295f1575ae9108ea62c12c83b1dd4db1`: the plan records its bundle at 541,184 bytes (lines 658 and 1928), and a file of that size is tracked at `notes/matched_cborg_2026-09-13/kids_first/KIDS_FIRST_preprocessed.txt`, with a chunk manifest beside it; an omission context is tracked at `data/omission_contexts/kids_first_omission_context.json`. No source manifest entry declares any of it, and `data/preprocessed/` holds no Kids First bundle or chunk manifest. So Kids First fails part (1) of the test as the inputs stand. NP1b repeats the test on the merged source, and that run decides.

That is different from missing: it is not counted in K_native (NP1.3), and plan §7's missing-cell rules apply only to in-scope cells (lines 347–349). Inputs added after NP1b do not bring a project in; that needs a prospective amendment.

## NP1.3 Roles, comparator and what can be claimed
- **The comparator is the plan's** (lines 474–488): the v8 API package. For CHORUS, CM4AI and VOICE it is the nine v8 API records the plan lists; for AI_READI it follows D64, item 14 (below).
- **What a native-against-v8 comparison is.** The plan's package effect (estimand 2, lines 453–460) compares generic_v10 API cells with v8 API records. Both sides ran through the provider route without tools. A native production cell differs from a v8 record in two sets of things at once:
  - **what plan §4 lists** between v8 and v10 (lines 908–973), including: the prompt, the harness, coverage timing, the schema, the caps, the thinking display, gating and selection, and the check instruments; the recall rule and the newly exposed Software keys (lines 955–958), which prediction 3 is read with; provider-side model drift (lines 959–961); effort (lines 962–964); and repository state (lines 965–968);
  - **what N1.6 declares between the arms:** effort (explicit high, against the provider default); runtime and transport (a subscription CLI, not a provider route), and with them the account; tools (Read, Write and Bash plus the permitted lookups, against none); staged exposure (the typed-helper phases); context (1M); no write-time normaliser; absolute local paths in the instruction (D126); and the D91 shared-v1 protocol differences in place of BC1;
  - **the schema release.** The native arm runs 3.2.1 under N1.8(h). N1.6 declares that against the API arm's ratified 3.1.0. Against the v8 records the difference is 3.2.1 against 2.0.0 (the plan's own row is "2.0.0 against 3.0.0", line 922); that statement is this amendment's.
- **So a difference between native v10 cells and v8 records is a package-and-runtime difference.** Nothing in it attributes an effect to the prompt package, to the runtime or to any one component. The plan counts in K the projects "whose contrast is like-for-like" (lines 836–837); this contrast is like-for-like in the source bundle only, and each registration verifies that identity (lines 936–938).
- **Role** [proposed, NP1.10(i)]: native production cells are the study's primary generic_v10 cells (D134). A native result is never pooled with an API v10 cell and never reported as the plan's package effect.
- **Comparison rules** [proposed, NP1.10(j)]: each rule the plan fixed for a v10-against-v8 comparison is applied to the native replicate cells unchanged: metric, instrument, analysis set, tolerance, missingness rule and per-project verdict.
  - Every result is reported under the label **"native v10 against v8 API: package and runtime"**. A prediction's overall statement reads "holds in k of K_native projects (package and runtime)".
  - D134 makes the native arm the main result. It does not say that the plan's tolerances and verdict rules transfer to it; that is this item.
  - **If the answer is no:** native production is descriptive only: per project, native values beside v8's with mean, SD and range, and no verdict (the default the plan describes at lines 822–824). The role above can stand with either answer.
- **K_native** [proposed, NP1.10(k)] counts the in-scope projects among CHORUS, CM4AI and VOICE, and AI_READI only when its comparator's record hashes were pinned at NP1b (below). The n=1 cells and a descriptive project are never in it.
  - **It is fixed once,** in the document that registers the floor's value (NP1.7 step 6): in NP1b when no pilot is pending, otherwise in the floor's own amendment, after every pending pilot has concluded. That is after every event that can remove a project from scope and before any production cell registers.
  - **It never moves afterwards.** A project in K_native stays in the denominator whatever happens to its cells. Its verdict is read by the plan's missing-data rule (lines 844–853). A primary verdict needs complete n=3 on each side under Set A definition (2), which means three cells that each have an eligible full record, accepted or not (lines 1102–1104), and every snapshot and block the metric requires, measured. A project without that counts as "not measured" in "k of K_native". Using both attempts of a cell does not by itself make a project "not measured".

  - **If NP1.10(r) is answered no,** the rule reads `with_receipt / receiptable` on the final record in place of the at-receipt counters, and is otherwise the same, except that the two-reading check below does not apply.
  - **Eligible pilots:** CHORUS's pilot and, if NP1.10(e) is yes and AI_READI is in scope, the AI_READI native pilot. **CHORUS's pilot** is the N1 canary where it meets both of NP1.10(aj)'s conditions, and otherwise the replacement pilot. Only an accepted attempt's saved result supplies a fraction; a rejected, stopped or assisted attempt never does (lines 1129–1133).
  - **Which reading: one.** Each pilot contributes one fraction, from the `slots` of its final-stage receipt check: the block the controller writes with `native_receipt_stage: final` (`native_shared_receipts.py:484–498`), read from the accepted attempt's saved result.
  - **The second reading is a check, never an input.** On the at-receipt basis the receipt-completion stage's `after` block is the checker run on the sealed original with the completed receipt (`:433–437`), so it should equal the final-stage pair. It is reported beside it. If the two differ, that is an instrument defect: it is filed as a finding, and the rule yields no value while it is unresolved. The floor's registration never chooses between two observed ratios. **The check applies on the at-receipt basis only.** On the final-record basis the two readings differ by design: the completion stage's `after` block reads the phase-1 record, and the gated ratio reads the final record.
  - **Readings that are not used.** The controller also evaluates the floor at the initial receipt check, where it forces the state to pending (`:363–364`). That is reported. It does not enter the rule and does not gate a production record. Final-record coverage is reported for every record as the plan's descriptive quantity.
  - **What gates in production:** the final-stage check's reading on the chosen basis, against the registered fraction (above, and NP1.6).
  - **A pilot whose saved result has no such reading** supplies no fraction, and the "no value" case below applies.
  - **Arithmetic:** exact integers, `floor(20 × with_receipt_at_receipt / receiptable_at_receipt) / 20`, then the minimum with 19/20, registered as a numerator over the denominator 20.
  - **Why the cap:** the plan's reason (lines 1134–1140). Receipt completion drives the at-receipt ratio towards 1, and a floor of 1 would stop a replicate on one unreceipted leaf.
  - **The lowest value that can be registered is 1/20.** The plan's rule rests on a re-canary that has passed its own 19/20 gate (lines 1147–1149). The native canary is ungated (D109), so the native floor is wholly the pilots' own reading. A low reading registers a low floor, which gates little. The value is reported with that said, and every production record's coverage is reported whatever the floor. A reading under 1/20 yields no value.
  - **The AI_READI branch.** NP1.6's table says how the pilot concludes. While it is pending the rule yields no value (below). If it concludes with no value for a cause that is not rule-level, AI_READI leaves scope as infeasible, reported as a feasibility result, and CHORUS's pilot alone sets the value (plan step 8, lines 307–312). A rule-level rejection is NP1.6's case.
  - **No value:** if a pilot the branch still requires has no accepted attempt, because it concluded with none or is still pending, or has a zero denominator; if the value comes to 0/20; or, on the at-receipt basis, while an instrument finding on the two readings is open, the rule yields no value. No production cell registers until a prospective amendment, reviewed as this one, supplies one. No other observed ratio is substituted (lines 1150–1152).
  - **Conformance, not choice.** The floor's registration confirms from the merged source that these are still the fields. If the merged source differs, the rule yields no value until a prospective amendment restates it.
- **How the value is registered** [proposed, NP1.10(z)]: in a dated amendment that gets this amendment's review and the owner's ratification. It checks the arithmetic and the inputs and does not revisit the rule (lines 1159–1163).

So a production attempt whose final authoritative floor assessment remains failed does not reach the recorder, and row B0 fails with it. A failed check that a permitted correction and a passing check supersede is not that (NP1.5). The attempt is classified by its cause, a content slip, not as a controller fault.

- **The owner signs each acceptance record** (D36). [proposed, NP1.10(v)] The record keeps every heading of plan §6 (lines 1026–1048), with these native entries. **Identities:** the registration sha256 and the artifact sha256s stay; the roster sha256 has no native counterpart and is recorded as not applicable; the native identities N1.6 lists are added. **Check rows:** N1.4(B)'s rows B0–B7, in place of the plan's item-5 rows. **Clean-run checks:** the checks N1.4(B) puts on the saved result, in place of the journal and override checks, which are the API runner's. **Cost:** the runtime's own cost estimate and the usage-window readings, in place of "at that day's prices". - **Attempts** [proposed, NP1.10(w)]:
  - **At most two attempts per native production cell,** counted across every label and registration, then the owner reviews. This is the plan's bound (§7, lines 1066–1069; D07), which D113 already applies to the canary.
  - **An attempt** is one launch that consumed its reservation. A capture is not an attempt, and a refusal before the reservation consumes none. A capture that is fresh at the reservation but stale at dispatch stops the attempt, and it counts (N1.5).
  - **Every attempt is retained,** stopped and rejected ones included (lines 1052–1056). A stopped or rejected attempt is never resumed or re-run under its label; any new attempt needs a new label, registration and word (N1.5; D56).

The class fixes the next action, and the next action is the plan's. The canary's endings are classed the same way for this amendment's purposes (below).
  - **The termination mechanism is recorded separately and never decides the class.** The mechanism is what ended the process: the registered deadline, the registered dollar guard, a usage stop, a manual stop, a helper's terminal refusal, or the runtime's own end. An attempt that ended on the deadline is rule-level if row 2 matches, a content slip if row 3 does, and budget or clock only if no earlier row matches. "A content defect outranks every operational class" (line 1361).
  - **The canary's classification, for this amendment.** N1.5 says "a **transport, budget or environment stop** (deadline, usage, dollar guard, host) is not a scientific rejection". Where the two differ, this amendment's reading decides what the canary means for production.   - **"The final records" of a stopped attempt** are its eligible full record (NP1.4) and that record's core.
