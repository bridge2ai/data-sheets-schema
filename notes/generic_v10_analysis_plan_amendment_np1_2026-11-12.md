An interpreter at another path makes them "cannot decide", a hold until the move is undone (the checkout, below). The registry also pins the package's own source files by digest (`native_shared_registration.py:141–144`, `:253–254`, `:266–279`), but not the third-party distributions, although the helpers execute LinkML, the term validator and their dependencies. Those are bound by the environment manifest (below), which the gate holds identical and which is checked again at dispatch. So a rebuilt environment whose distributions or installed files differ makes later registrations not equal, and a change after a registration is prepared holds its launch;
    - **the checkout.** Its absolute path is recorded as the working directory and in every absolute pin, and the validators the gate runs reconstruct it from the process that runs them (`native_shared_registration.py:113–120`, `:245–246`). Launch re-verification refuses unless the working directory is the code's own root and equals the packet's recorded one, and unless the interpreter's path and version equal the running ones (`native_shared_registration_orchestration.py:168–170`, `:236–238`). So the checkout path is an identical field: every registration of the stratum is built in the reference's checkout, at its path, and the files the registration pins must not change. A path is not a sha256 pin, so a registration built after the checkout or the interpreter has moved cannot be validated at the reference's path, and the gate's result is "cannot decide" (NP1.5's precedence, below). It is a hold until the move is undone, and restoring the paths allows another comparison. A move that cannot be undone is a pre-reservation defect under NP1.10(ar);
    - **the reference's source export and saved files.** At every later registration the gate validates the reference's packet with the production validators, run from the reference's own source bytes (below). Validating a runtime declaration reads its saved probe and request files again and pins the durable copy again, comparing its path, device and inode as well as its bytes (`native_u4b_runtime.py:288–302`). So the source export, the packet, its saved files and the copy itself stay unchanged, the copy at the same path, until the last production cell's acceptance record is signed. A copy replaced by an identical file is a different file to that check, and it cannot be put back: the registrations after it cannot validate, which is a pre-reservation defect under NP1.10(ar);
    - **the probe's limits.** The runtime declaration's `limits`, which each registration takes from its own observation probe (N1.2), are identical fields, so a change on the provider's side in the reported limits makes later registrations not equal, as a binary update would. Whether those values can change while the binary stays the same is not known.
- **The gate** [proposed, part of NP1.10(al)]: a comparison of the registrations' pins and declared values, not a replay (the lead's decision, Authority). It is a script with a data file. **The data file is a closed field-level schema:** it classifies every field a registration packet records into one of three kinds, under the principle below. Both are an engineering prerequisite, due before the canary's registration, assigned and not written (NP1.7).
  - **What runs** (the lead's rulings, Authority). The gate runs no attempt and no behavioural replay, and calls no model and no binary. The only code it runs is the existing production validators, read-only, in an isolated process, at the reference's checkout path and under the reference's interpreter, from source bytes it has first verified to equal the reference run's own source export. It never runs bytes that differ from the reference's pins, so the candidate's code is never executed where it differs from the reference's. The validators reconstruct the derived values deterministically, the rendered instruction and the command guidance among them (`native_shared_registration.py:95–97`, `:110–111`, `:256`, audit, from the Claude review of v10). That reconstruction is part of validation, not a replay. The comparison of fields then reads data only.
  - **The principle.**
    1. **Identical:** every value that can change what runs, what the model reads or how acceptance is decided. Among them: the pins of the package source and of every other pinned file, the prompt assets, the `.claude` command and agent files, the schema closure, the closed dependency registry, the Claude Code binary's sha256, the base system-instructions bytes, the checkout path, the interpreter's identity and path, the environment manifest, the profile, the selection bounds (NP1.10(ap)), the run limits and every other runtime value, the values the observation probe records about the model and its limits, and every scientific registered value. A value that decides what runs is identical even where it is written as a path, such as the executable search path.
    2. **Per-run:** a value that only names or locates this run, even where the model reads it, as the model reads the run's own label and absolute paths (D126). Among them: identifiers (registration, selection, job, attempt and session, and the receipt-policy registration's `registration_id`), labels, the run's project, timestamps and validity dates, and the device and inode numbers that fingerprints record. Among paths, only these are per-run: the per-attempt roots (attempt, evidence, output and stage) and the paths under them, and the paths of the per-registration files, which each registration writes for itself and so cannot place at the reference's paths: the registration and its selection, composition, runtime declaration, environment manifest, instruction, probe and receipt-policy registration files. Their contents are judged by the rules here, never by their paths. Every other path is identical, and the data file names each path field and its class. The project-input fields are per-run only as far as the rule on a project's inputs allows (below).
    3. **Derived:** a value that pinned code computes from the fields above. Among them: the embedded preparation and composition documents, the command line and the environment, the command guidance appended to the system prompt, the selection, preparation, composition, policy, instruction, probe and expectation hashes, and the byte counts recorded beside them. The gate recomputes each from the candidate's own content and requires it to validate. A derived value is never merely exempted, and a whole embedded document classed as derived never hides one of its leaves from the identical check (below).
  - **Every leaf is classified.** A machine-checkable inventory lists every leaf of every document the packet records, the documents embedded as JSON and the collections with variable keys included, and gives each its class. A leaf the schema does not classify is "cannot decide" (below). The data file names each field by its location in the registration packet that the merged source builds, and both reviewers check it against that source.
  - **A project's inputs** must equal that project's input tuple pinned at NP1b, exactly: the four input files a selection pins, each by sha256, which are the study's source manifest as one whole file and the project's bundle, chunk manifest and generation (omission) context (NP1.2). Their sha256s cover the project's scope declaration, which sits inside the context and the source manifest. The reference's tuple is CHORUS's. A change to a tuple needs a prospective amendment; until one is ratified, a registration with other inputs is not equal.
  - **The environment manifest** (the lead's rulings, Authority).
    - **The documents.** Per the lead's record, the registration's preparation and execution documents take successor kinds, version 3: `d4d_native_shared_preparation_v3` and `d4d_native_shared_execution_registration_v3`. The preparation carries one more required file pin, `environment_manifest`, to a closed, versioned document of kind `d4d_native_environment_manifest`, and the execution binds it through the preparation it embeds. Once version 3 is in the source, version 2 documents stay readable as historical evidence only, and no route accepts them for a new registration.
    - **What it records.** The interpreter's semantic identity: its implementation, version and build. And, sorted and unique, each third-party distribution the native interpreter can import, with its name, its version and the sha256 of its installed `RECORD` file. The project's own package is covered by the source pins and is not in it.
    - **What generating it checks.** It is regenerated at preparation and again at dispatch. Each time, every installed file that a distribution's `RECORD` lists with a hash is read and checked against that hash. Entries listed without a hash, such as the `RECORD` file itself and compiled `.pyc` files, are named in the manifest as unverified, by kind, with their count. A mismatch, a missing or unreadable file, missing, ambiguous or unreadable metadata, or an editable or development install of a third-party distribution holds: the registration is not prepared, or the launch does not proceed.
    - **At dispatch.** The regenerated manifest must equal the pinned one, or the launch holds. NP1b names, from the merged source, whether this check comes before the attempt's reservation. Before it, a hold spends no attempt. After it, the attempt stops and counts, as a capture that is fresh at the reservation but stale at dispatch does (N1.5).
    - **In the gate** it is an identical field, as the interpreter's identity and path are.
    - **Its deadline** is the CHORUS reference pilot's registration at the latest, and the canary's registration if NP1.10(as) is answered yes (NP1.7).
  - **The floor's change** is the one permitted change of an identical value, and it is checked separately.
    - **What the floor's registration document carries.** It is a receipt-policy registration: a JSON document with exactly seven fields (`native_shared_contract.py:785–813`, at the candidate): `kind`, `version`, `registration_id`, `condition`, `runtime_policy_sha256` (the policy asset's sha256), `receipt_instrument_version` (4) and `coverage_floor`. A pending floor is exactly `{state: pending, mode: diagnostic_pilot}`; a registered one is exactly `{state: registered, numerator, denominator, basis: receipted_part}`.
    - **The floor's registration** (NP1.7 step 6) is the reference's receipt-policy registration with `coverage_floor` replaced by the registered value and its basis. Its `registration_id` is a per-run field, as every identifier is, and it may be new. Every other field is the reference's. It is written at its own path: a selection pins its receipt-policy registration as a file, path and bytes together (`native_shared_contract.py:754`; `native_shared_selection.py:207–208`, `:377–383`; at the candidate), and the reference's pending registration stays at its own path, so that the reference's packet validates again at every later registration. That path is per-run (above).
    - **The check.** The gate requires that the production cell's floor value and basis are exactly those of the floor's ratified registration, computed by NP1.10(s)'s arithmetic, and that every other field of its receipt-policy registration, `registration_id` apart, is identical to the reference's. The receipt-policy registration's path may differ from the reference's; the file it names is checked as the floor's registration. The hashes that carry it are derived values and are recomputed. **A structurally valid floor value other than the ratified one is "not equal".** A basis other than `receipted_part`, or none, is refused by the receipt-policy parser (`native_shared_contract.py:803–806`, at the candidate), which the validators run when they rebuild the selection (`native_shared_selection.py:399`, at the candidate); that packet fails validation, and the result is "cannot decide" (below). What that one value does inside a run, where helper output shows "pending" in a pilot and "passed" in production, is the pinned code acting on that value. It is never compared, because no run is executed.
  - **The comparison-input manifest.** Before it compares anything, the gate writes an immutable manifest that names its inputs by path and sha256: the reference's registration packet and the candidate's, each as the registration builder wrote it, before any gate result or review is added; the floor's registration, where it applies; the project's input tuple; the gate's script and data file; and the reference's source export, by the digests the gate checked it against. The manifest's sha256 covers the manifest file's bytes. The gate's result names that sha256, and the result and the registration's two reviews go in an outer evidence packet that refers to these hashes. No hash covers a file that refers back to it.
  - **Three results, disjoint, and their precedence.**
    - **The shortcut.** A must-equal implementation or asset pin whose recorded sha256 differs from the reference's establishes a prohibited difference from the pins alone, before any validation of the candidate, but only where that pin is valid: both packets can be read that far, its record is well formed, the data file classes its location as a must-equal implementation or asset pin, and the reference's packet has passed the validators. A project-tuple substitution, a derived value and the floor's transition never take the shortcut: they are judged only after both packets pass the validators. The environment manifest's pin is a must-equal implementation pin, and so are the dependency registry's sha256 pins, the interpreter's among them: each takes the shortcut. A path is not a sha256 pin and never takes it.
    - **Equal:** both packets pass the production validators, every leaf is classified, every identical field is byte-identical, every derived field validates, the inputs equal the project's tuple, and the floor's change, where present, checks.
    - **Not equal:** a prohibited difference is established on valid evidence: by the shortcut, or, after both packets pass the validators, an identical field that differs, a project-input field that does not match the tuple, a floor value other than the floor's ratified registration's, or bounds other than the stratum's. It is the result even where other evidence is invalid, missing or unclassified. The registration is not made under this amendment.
    - **Cannot decide:** no prohibited difference is established, and some evidence is invalid or incomplete: a packet fails the production validators (among them a packet with a wrong or missing floor basis, and one built after the checkout or the interpreter moved), a pinned file is missing, a leaf is not classified, or a derived value cannot be recomputed. It is a hold: that registration is not made until the cause is resolved. It is never a pass and never a reason for another pilot.
    - **What the result lists:** every difference and every evidence problem the gate established, not only the first. Where the shortcut decided, it says that the candidate was not validated.
  - **A defect in the gate itself.** Before the reference exists, the data file and the script are corrected and reviewed again, and the demonstration below is repeated. After the reference run, a "cannot decide" or a wrong result whose cause is in the gate's own script or data file is a comparison defect under NP1.10(ar): both reviewers confirm it, and its repair changes the gate's bytes, so the stratum ends at the boundary that item fixes. The gate is never run again with an edited list inside this stratum.
  - **Demonstrated before the canary's registration, and again whenever the format changes.** Both reviewers review the data file against this section, and the gate is run on registration packets built by the registration builder: rehearsal packets with the real structure, whose synthetic values are marked as synthetic in their bytes. The inventory is part of the demonstration: it shows every leaf classified. The demonstration also shows whether the unchanged validators accept a permission probe rebuilt offline for a packet's own selection and marked synthetic, which decides the rule for the run on the reference pilot's own packet (below). The saved output shows each case's result and the fields it names:
    - **equal:** a packet against itself; against the same project's later registration; against another project's registration, rebuilt with fresh identities, paths and dates and with that project's tuple; a valid transition from a pending floor to a registered one; a reference whose registered validity has passed, since a registration is valid for two weeks (amendment N1's item (g)) and production may well take longer; and a reference whose attempt has consumed its reservation;
    - **not equal:** a changed prompt asset; a changed binary hash; a changed bound; a changed interpreter whose bytes differ, by the dependency registry's sha256 pin of them, on either format; a wrong floor value that is structurally valid; an internally valid registration with another project's tuple; two prohibited differences together, both listed; and, on a format that carries the environment manifest, a changed interpreter version, a changed version of a third-party distribution and a changed installed file of one, by the manifest's pin;
    - **cannot decide:** a missing artifact; an unknown field; an incorrect derived binding; invalid evidence; a wrong or missing floor basis, which the parser refuses; a moved checkout or interpreter path, on either format, a hold until the move is undone; and, on version 2, which has no environment manifest, a changed interpreter version with the interpreter's bytes unchanged;
    - **the mixed case:** a prohibited difference in a valid must-equal pin together with invalid evidence elsewhere gives "not equal", listing both.

    The results are recorded with the canary's registration. If the demonstration fails, the data file is corrected before the canary, not after any reference exists. **Whenever a change before the reference changes the registration format,** the version 3 documents among them, the demonstration is repeated on the new format before the first registration on it, and recorded with that registration. **The environment-manifest cases follow NP1.10(as), which the owner has not answered.** They are the cases decided by the manifest's pin (above). If (as) is answered no, the canary registers on version 2, which carries no manifest: those cases are not applicable before the canary, and the complete version 3 demonstration, those cases included, is required before the first version 3 registration. If (as) is answered yes, they are required before the canary's registration, with the rest of the demonstration.
  - **Run on the reference pilot's own packet, before each of its launch words.** Before the launch word of each registration of the CHORUS reference pilot, the gate is run as production will run it, with that registration's own packet as the reference, against:
    1. **itself,** with the inventory run on that real packet and showing every leaf classified;
    2. **a packet for each other in-scope project,** built offline by the registration builder from the same source, with that project's real input tuple pinned at NP1b. Where no other project is in scope, as with CHORUS alone (NP1.2), this case is recorded as "not applicable";
    3. **the reference pilot's packet with the floor's registration substituted:** a receipt-policy registration built as the floor's registration will be built, at its own path, carrying a registered floor and its basis with the value marked synthetic, and that synthetic registration as the floor's input.

    Each must give "equal", apart from a case recorded as "not applicable". This is in addition to the demonstration above. The results go in that registration's outer evidence packet, and its reviews name the sha256s of each run's comparison-input manifest and result (NP1.10(aa)), so its coded word binds them.
    - **The permission probes of packets (2) and (3).** The validators require a saved permission probe whose binding names the packet's own selection, instruction and system hashes (`native_shared_registration.py:168–180`, `:256–264`; `native_shared_permissions.py:1015–1019`), and only a binary call makes a real one. Two rules are fixed here, and neither changes a validator. **(i)** Each packet carries a permission probe rebuilt offline for its own selection and marked synthetic in the comparison-input manifest, and the unchanged validators accept it. **(ii)** If the demonstration shows that the unchanged validators cannot accept such a probe, the gate validates (2) and (3) with only the saved-probe check replaced by a recomputation of the expected binding, and its result lists that substitution. Which rule applies is a property of the validators, which the demonstration shows before the first registration on that format; no native outcome bears on it.
    - **A failure.** A cause in the gate itself, such as a leaf the inventory does not classify, a wrong class or an error in the script, is a defect in the gate: the data file or the script is corrected and reviewed, and this run and the demonstration are repeated, before that word. A refusal of packet (2) or (3) by the validators is corrected in that packet's construction before that word. The gate's rule and data file are never changed to make a case pass.
    - **Which gate later comparisons use.** Every comparison after the reference names the script and data file last run under this rule on the reference run's own registration.
    - **What it shows, and what it does not.** It runs the gate on the real format and runtime profile of the packet that becomes the reference, on every other in-scope project's real inputs, and on the floor's transition, which every production registration takes. The packets built offline make no binary call: their permission probes follow rule (i) or (ii) above, and the result says which. Where they cannot carry other evidence that only a binary call makes, the run records which fields stand in for it and how they are classed, and both reviewers check that no identical field was exempted to make a case pass. So it shows the gate's classification on production's format; it does not show that a real registration for another project will validate, or that a real probe will pass.
  - **When it runs in production.** The gate is run on every registration made after the reference exists, and must say "equal", before that attempt's launch word is asked for. A registration that is not equal cannot be launched under this amendment, and a registration made after a boundary is not in this stratum whatever the gate says.
  - **What the reviewers do.** NP1.10(aa) (NP1.7). Each review of a registration made after the reference exists names the sha256s of the comparison-input manifest and of the gate's result, and each review of a registration of the CHORUS reference pilot names those of each run on its own packet. The coded word names the review bundle that carries both reviews (N1.9 item 4), so it binds the results it was given on.
  - **What it cannot show.** That the provider's model is the same from run to run; the plan declares that drift (lines 959–961). And nothing about behaviour: it shows that a run was given the reference's code, assets, binary, bounds and rules, with only the per-run fields changed and the derived ones recomputed.
  - **The selection bounds** [proposed, NP1.10(ap)]. The bounds are values each registration supplies, inside ceilings the source fixes (`native_shared_contract.py:109–120`), and they gate a run: an input larger than its bound is refused (`:777–779`); an inventory larger than its bound stops the receipt check, and a stage request larger than its bound is refused (`native_shared_receipts.py:337–338`; `native_shared_stage/__init__.py:342–343`; audit, from the Claude review of v8). No code computes them. **One set of values for every registration of the stratum and for the canary,** chosen before the canary's registration from the largest input the study's source manifest declares, with a stated margin, inside the contract's ceilings. The gate compares them byte for byte. This is the lead's decision (Authority), put to the owner here. Because the canary uses the same values, the shakedown exercises them, and NP1.2's inputs test reads them. The derivation is given bound by bound, for each key the contract's ceilings name: the property of the largest declared input it follows from, which need not be bundle bytes, its margin, and why it fits under its ceiling. The values and their derivation are reviewed with the gate's data file and recorded with the canary's registration. It is an engineering prerequisite (NP1.7). **What the canary shows changes no bound.** The values are fixed before the canary's registration, and every later registration keeps them (NP1.6). A bound found too small is corrected before the reference only by a ratified change to this amendment, under the bar, and after it only in a new stratum. A pilot stopped by a run-time bound is classed by NP1.6 like any other stop; where that is an impossible limit (row 5), the pilot concludes without acceptance, and for AI_READI that takes it out of scope (NP1.6).
  - **Where the run limits stand.** With the four protected files the owner approved (D139), the instruction's recorder command carries `--render-spec-json`, whose value embeds the raw runtime declaration, and that declaration contains `deadline_seconds` and `budget_guard_usd` (`api_runner.py:1194–1211`; `native_shared_render.py:205–212`, `:289–295`, `:378–380`; `native_shared_runtime_constants.py:8–9`; read by the lead at `6561dac3c3af50cbfce1ba3c8b6ad21d9cd4b834`). The lead decided to pass the render specification through the controller's environment before the canary (#6065), which takes it out of the recorder line; per the lead's record that change is on the published candidate (NP1.7). The gate depends on neither: the limit set is a registered value, so the canary's registration, which declares amendment N1's set, is never equal to a production registration.
- **The rule** [proposed, NP1.10(s)]. It is the plan's floor rule (§8, lines 1125–1127) read for native pilots, and it takes no value from the API arm:

> The registered native coverage floor is the lowest of the eligible native pilots' D37 at-receipt coverage fractions, `with_receipt_at_receipt / receiptable_at_receipt`, rounded down to a multiple of 1/20 and capped at 19/20.

  - **Eligible pilots:** the reference run, which is the first accepted attempt of the CHORUS reference pilot (above), and, if NP1.10(e) is yes and AI_READI is in scope, the AI_READI native pilot. **The canary's reading is reported and is never an input;** that supersedes D109's clause quoted above. Only an accepted attempt's saved result supplies a fraction; a rejected, stopped or assisted attempt never does (lines 1129–1133).
  - **Which reading: one.** Each pilot contributes one fraction, from the `slots` of its final-stage receipt check: the block the controller writes with `native_receipt_stage: final` (`native_shared_receipts.py:484–498`), read from the accepted attempt's saved result.
  - **The second reading is a check, never an input.** On the at-receipt basis the receipt-completion stage's `after` block is the checker run on the sealed original with the completed receipt (`:433–437`), so it should equal the final-stage pair. It is reported beside it. If the two differ, that is an instrument defect: it is filed as a finding, and the floor is not registered while it is unresolved. The floor's registration never chooses between two observed ratios. **The check applies on the at-receipt basis only.** On the final-record basis the two readings differ by design: the completion stage's `after` block reads the phase-1 record, and the gated ratio reads the final record.
  - **Readings that are not used.** The controller also evaluates the floor at the initial receipt check, where it forces the state to pending (`:363–364`). That is reported. It does not enter the rule and does not gate a production record. Final-record coverage is reported for every record as the plan's descriptive quantity.
  - **What gates in production:** the final-stage check's reading on the chosen basis, against the registered fraction (above, and NP1.6).
  - **An accepted pilot whose saved result has no such reading** supplies no fraction. Its project stays in scope, and the floor is not registered (below).
  - **Arithmetic:** exact integers, `floor(20 × with_receipt_at_receipt / receiptable_at_receipt) / 20`, then the minimum with 19/20, registered as a numerator over the denominator 20.
  - **Why the cap:** the plan's reason (lines 1134–1140). Receipt completion drives the at-receipt ratio towards 1, and a floor of 1 would stop a replicate on one unreceipted leaf.
  - **The lowest value that can be registered is 1/20.** The plan's rule rests on a re-canary that has passed its own 19/20 gate (lines 1147–1149). The native canary is ungated (D109), so the native floor is wholly the pilots' own reading. A low reading registers a low floor, which gates little. The value is reported with that said, and every production record's coverage is reported whatever the floor. A reading under 1/20 cannot be registered: the pilot's project stays in scope, and the floor is not registered (below).
  - **The AI_READI branch.** NP1.6's table says how the pilot concludes. While it is pending the floor waits (below). If it concludes without acceptance for a cause that is not rule-level, AI_READI leaves scope as infeasible, reported as a feasibility result, and the CHORUS reference run alone sets the value (plan step 8, lines 307–312). A rule-level rejection is NP1.6's case. An accepted AI_READI pilot never takes AI_READI out of scope, whatever its reading.
  - **When the floor is not registered.** In each of these cases no production cell registers, and no other observed ratio is substituted (lines 1150–1152):
    - **a required pilot is still pending,** or waits on an instrument or unknown case (NP1.6): the floor waits for it;
    - **an instrument finding on the two readings is open:** the floor waits until it is resolved;
    - **an accepted pilot has no usable fraction:** its saved result has no final-stage reading, its denominator is zero, or its reading is under 1/20. Its project stays in scope. A prospective amendment, reviewed as this one, says how the floor is set; it is under the bar, which says what it may apply (above);
    - **there is no reference run,** because the CHORUS reference pilot concluded without acceptance (NP1.6): a prospective amendment says how the condition proceeds;
    - **the gate's result for the AI_READI pilot's registration is "cannot decide":** that registration waits, and so does the floor. Where the cause is a defect under NP1.10(ar), as a cause in the gate itself is, the floor does not wait: this stratum ends at the filing, before the floor and before any production cell;
    - **the reference run's source no longer saves the fields this rule reads:** the floor waits for a prospective amendment that restates them (below).

    An AI_READI pilot that concludes without acceptance for a cause that is not rule-level is not one of these cases: AI_READI leaves scope, and the CHORUS reference run alone sets the value.
  - **Conformance, not choice.** The floor's registration confirms from the reference run's source that these are still the fields. If they are not, the floor is not registered until a prospective amendment restates it.
- **How the value is registered** [proposed, NP1.10(z)]: in a dated amendment that gets this amendment's review and the owner's ratification. It checks the arithmetic and the inputs and does not revisit the rule (lines 1159–1163). The document it registers is the reference's receipt-policy registration with `coverage_floor` replaced (the gate, above).

## NP1.6 Acceptance, attempts and stops
- **Each attempt is judged by N1.4(B)'s rows B0–B7** [proposed, NP1.10(u)], as ratified, on the saved result after the attempt ends. N1 wrote those rows for the canary. Applying them to the AI_READI pilot, to the CHORUS reference pilot and to every production cell is this amendment's proposal.
  - **Row B0 for production.** N1 wrote B0 for a pending floor: "The receipts gate uses the structural floors only, so D109's pending floor doesn't block it." For a production cell B0 reads the receipts gate with the structural floors and the registered coverage floor.
- **For production cells, row B5 gates** [proposed, NP1.10(t)]: the final-stage floor reading (NP1.5) must read `state: passed` under the registered floor. Pilots keep B5 reported and labelled UNMEASURABLE (D109). "Accepted" for a production cell then means B0–B7 all hold.
  - **Where a registered floor is enforced.** Inside the run, by the final strict receipt check. After the run, at finalization, by the receipts gate (audit). So a production attempt with a floor failure, as NP1.5 defines it, does not reach the recorder, and row B0 fails with it. A failed check that a permitted correction and a passing check supersede is not a floor failure, and neither is an assessment that is unmeasurable or not applicable (NP1.5). A floor failure is classified by its cause, a content slip, not as a controller fault. The other cases are classified by the plan's precedence.
