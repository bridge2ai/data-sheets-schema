## NP1.2 Cells, scope and order
- **The cells (D135):** three replicates each for CHORUS, CM4AI, VOICE and AI_READI, and one each for VOICE_PEDIATRIC and Kids First if in scope. NP1.10(c) proposes that Kids First is not planned under this amendment (below). Records go under `claudecode_direct{,_core}/<label>/` (D27; N1.1).
- **A cell** is (arm, project, replicate position), as plan §3 defines it (lines 715–718). Each registration declares the position it fills. This amendment uses "cell" only in that sense. The whole native arm under the shared-v1 protocol is called **the native shared-v1 condition**.
- **A production cell** [proposed, NP1.10(d)] is any cell of this amendment that is not a pilot: the twelve replicate cells and VOICE_PEDIATRIC's descriptive cell. Every one of them that is in scope, thirteen for the study's five projects, runs under the registered floor and under NP1.6's acceptance rows, attempt bound, classification and stop-loss. Only the twelve replicate cells can enter a verdict.
- **The N1 canary is never one of these cells** (D25, D107; N1.5), and neither is a pilot.
- **Scope rule** [proposed, NP1.10(a)]: the plan's rule (lines 333–355), narrowed for the native arm.
  - **Whole projects only.** A project is in or out with all its cells. Replicates are never trimmed inside a project.
  - **The order** is the plan's (lines 340–344): CHORUS ×3 → CM4AI ×3 → VOICE ×3 → AI_READI (pilot + ×3) → VOICE_PEDIATRIC ×1. The plan's order ends with Kids First ×1, which this amendment does not plan (below). Under NP1.7 every pilot runs before the floor is registered and so before any production cell, as the plan's own pilot does (lines 307–312).
  - **Scope is decided at NP1b, by one test of inputs.** A project is in scope if all three hold at the merged source NP1b runs on: (1) the project's source manifest, named below, declares it, with a bundle and a chunk manifest; (2) the repository's own checks, run with that manifest, report that bundle and chunk manifest current (`d4d download audit-bundles` and `d4d bundle chunk --check`); (3) the production prepare and validate functions accept the first part of a registration for it, built from its real inputs: the receipt policy, the selection, the schema, prompt and profile pins and the byte inventory, with the selection bounds that the stratum's pinned selection-bounds rule gives for it (NP1.5) and the production limit set (NP1.7). NP1b records the commands, their saved outputs and each project's result, and both reviewers check them. NP1b runs the test on the exact source on which the CHORUS reference pilot registers, and the test is repeated there if that pilot's second attempt registers on a changed source (NP1.7).
  - **Which manifest the test reads, fixed here:** the study's source manifest, `data/preprocessed/source_manifest.yaml`, for all five projects. No other manifest is read for this test. NP1b records the sha256 of the manifest it read.
  - **What the test does not limit.** It tests that a project's inputs exist and are well formed. A final receipt check that fails and is then superseded, by a permitted correction, a fresh derivation and a passing check, is a transient helper failure; the phase rules allow that sequence (`native_shared_phase.py:24–25`, `:360–362`; and `:145–152`, audit, from the Codex review of v5). And an assessment that is pending, unavailable, unmeasurable or not applicable did not pass, but it is not failed: a zero denominator gives `state: not_applicable` (`native_shared_receipts.py:304–305`, audit, from the Codex review of v6). In the shared evaluator absent snapshot counters give `unmeasurable` (`receipt_completion_policy.py:385–387`, audit, same review). The native `floor()` has no such state at the cited commit (`native_shared_receipts.py:296–307`); it is to give it once the basis change makes it read the snapshot counters. Those are classified by the plan's existing rule, "Unmeasurable is not failed" (lines 1364–1366). On the at-receipt basis the gated ratio cannot move after receipt completion, so a failed final check stays failed. An attempt with a floor failure is not accepted. It has an eligible record only if the retention change is merged (NP1.10(n), answered keep), `derive_final_core` is a current check when the attempt ends, and no write to the full record or the core followed that check. The phase rules do not require the derivation before the final receipt check, though the instruction orders it first (audit, from the Codex review of v4: `native_shared_phase.py:195–202`, `native_shared_render.py:371–372`). This amendment adds no ordering requirement. Where a condition fails, the attempt is artifact-missing and is listed as such (NP1.4).
    - **A known behaviour.** A failed final receipt check is not a terminal helper (`native_shared_phase.py:24–25`, `:360–362`), and the instruction keeps every final check required (`native_shared_generation_v1.md`, lines 53–54). So a run that fails the registered floor at its final check can keep working until the deadline. The cost is the rest of that run: its time and its usage.
    - **Stopping at receipt completion instead** would change how attempts are stopped. That is a change of scientific procedure and a new stratum, under its own prospective amendment (NP1.7).
  - **The alternative that was offered, and not taken (D140):** the floor measured on the final record, as the code had it. It departs from D37 and from plan §8: removing unreceipted leaves after the seal raises the gated ratio, and reconciliation moves it in either direction. Its consequences, and the API values the lead had in view when the basis was put to the owner (plan lines 200–201; header), are written out in draft v7 (NP1.5).

- **No change may rest on a native result** [proposed, NP1.10(ao)]. The plan says of P4b: "It may not use any v10 quality value, A21's included, to choose a project or a threshold. Changing a rule needs its own prospective amendment, and it starts a new analysis stratum." (lines 322–325). This amendment carries that bar to everything that follows the canary.

- **The reference run** [proposed, NP1.10(al)]. One rule, with no pilot run again and no production source chosen.
  - **What it is.** The production stratum has one reference: **the first accepted attempt of the CHORUS reference pilot** (NP1.6), one native CHORUS pilot registered after NP1b and after the canary's acceptance, under the production limit set, with the floor pending. The canary is never the reference: it runs under amendment N1's limit set (NP1.10(ab), answered B), and a registered value that differs is never equal (below).
  - **What the reference fixes.** Everything that attempt's registration pinned: its package source and every other file it pins, its selected prompt assets, its schema closure, the closed dependency registry and its registered values. Three of those are things the model reads that are set per registration: **the Claude Code binary** (by sha256), **the base system-instructions file** (by sha256) and **the selection-bounds rule** (below). The system prompt the binary receives is that file followed by command guidance that pinned code generates from the registration's own values (`native_shared_registration.py:46`, `:247–256`, audit, from the Claude review of v7). The base file is compared byte for byte; the guidance is a per-run field (below).
  - **Every later registration is equal to the reference, or it is not in this stratum.** The AI_READI pilot's registration and every production cell's registration are compared with the reference by the gate below. **Equal:** the registration belongs to this stratum. **Not equal:** it does not, and it is not made under this amendment. **Which commit a registration was built from does not matter; only its pinned bytes do.** Nobody chooses a production commit, and nobody decides whether a difference matters.
  - **No pilot is run again.** A pilot's reading is never replaced by a second run of that pilot.
  - **Production runs on frozen code.** After the reference run, any change to a pinned file, to an asset, to the binary, to the base system instructions, to the selection-bounds rule, to the gate's own script or data file, or to a registered value outside the per-run list ends this stratum for the registrations made after it. Those need a new prospective amendment, which names its own pilots before any of them runs and is bound by the bar above. This stratum's floor, its K_native and its readings never move, and a reading that a later stratum does not use is still reported. **There is no "equal change":** a change either leaves every pinned byte as it was, or it ends the stratum. So D35's diagnostic canary does not arise inside this stratum (NP1.7).
  - **What this costs, and the precautions.** A repair of anything pinned cannot be taken into this stratum after the reference run, however small. The repairs the canary reveals go in before the CHORUS reference pilot registers (NP1.7). Two changes that nobody chooses would also end the stratum. **The binary:** the reference's pinned copy of the Claude Code binary is kept, unchanged and with automatic updates off for that copy, for all of production. **The probe's limits:** the runtime declaration's `limits`, which each registration takes from its own observation probe (N1.2), are registered values, so a change on the provider's side in the reported limits would end the stratum just as a binary update would. Whether those values can change while the binary stays the same is not known.
- **The gate** [proposed, part of NP1.10(al)]: a comparison of the registrations' pins, not a replay (the lead's decision, Authority). It is a script with a data file. Both are pinned by sha256 in the CHORUS reference pilot's registration packet, and both are reviewed against this section before NP1b (NP1.7): **an engineering prerequisite, assigned and not written.**
  - **What it reads:** two registration packets, the reference's and a candidate's, each first verified by the production validators. **Nothing from either source tree is executed.**
  - **Equal** if and only if every file the registration pins (the package source, the prompt assets, the `.claude` command and agent files, the schema closure and the closed dependency registry), the Claude Code binary's sha256, the base system-instructions bytes, the selection-bounds rule and every registered value are byte-identical to the reference's, except the fields on the per-run list.
  - **The per-run list,** in the gate's data file, names exactly these and nothing else:
    1. **the project's own inputs:** the bundle, the chunk manifest, the source-manifest entry, the omission context and the scope declaration, each by its pinned path and sha256;
    2. **the selection bounds' values.** The gate does not compare them with the reference's. It recomputes them under the pinned selection-bounds rule from the registration's own inputs, and requires them to equal what the registration declares;
    3. **identifiers:** the registration, selection, job and attempt identifiers;
    4. **timestamps,** in the format the registration declares;
    5. **paths under the attempt directory;**
    6. **the system prompt's command guidance,** which pinned code generates from the values above. The gate requires the generating code, which is pinned source, to be byte-identical, and records each registration's raw effective-system hash. An identity substitution in that guidance is not a change of the system prompt.
  - **The floor's change** is the one permitted change of a registered value, and it is validated separately. A pilot's receipt-policy registration carries `{state: pending, mode: diagnostic_pilot}`; a production cell's carries the registered fraction. The gate requires that the production cell's value and basis (`receipted_part`) are exactly those of the floor's ratified registration (NP1.7 step 6), computed by NP1.10(s)'s arithmetic, and that every other field of the receipt-policy registration is byte-identical. What that one value does inside a run, where helper output shows "pending" in a pilot and "passed" in production and the hashes that carry it differ, is the pinned code acting on that value. It is never compared, because nothing is executed.
  - **Three results.** **Equal.** **Not equal,** with every differing pin listed. **Cannot decide:** a packet fails its validators, or a field is neither byte-identical nor on the per-run list. "Cannot decide" is a hold: that registration is not made until the cause is repaired. It is never a pass and never a reason for another pilot. **A "cannot decide" whose cause is in the gate's own script or data file** is resolved only by a ratified prospective change to them, never by running the gate again with an edited list; until then that registration is not made.
  - **When it runs.** The gate is run on every later registration, and must say "equal", before that attempt's launch word is asked for. Its saved result names the script's, the data file's and both packets' sha256s, and is in the registration's packet. A registration that is not equal cannot be launched under this amendment.
  - **What the reviewers do.** The two reviewers of a registration confirm that the gate's script and data file are the pinned ones, that it was run on the right two packets, and that the saved result is the one in the packet. They do not interpret it.
  - **What it cannot show.** That the provider's model is the same from run to run; the plan declares that drift (lines 959–961). And nothing about behaviour: it shows that a run was given the reference's code, assets, binary and rules, with only the listed fields changed.
  - **The selection-bounds rule** [proposed, part of NP1.10(al)]. The bounds are values each registration supplies, inside ceilings the source fixes (`native_shared_contract.py:109–120`), and they gate a run: an input larger than its bound is refused (`:777–779`); an inventory larger than its bound stops the receipt check, and a stage request larger than its bound is refused (`native_shared_receipts.py:337–338`; `native_shared_stage/__init__.py:342–343`; audit, from the Claude review of v8). That review found no code that computes them. **This amendment requires a fixed rule:** a function from a project's inputs to its bounds, inside the source's ceilings, written down and pinned by sha256 with the gate. A rule that gives one set of values for every project, large enough for all of them, is a valid rule. It is fixed and reviewed before NP1b, which uses it in NP1.2's inputs test, and both attempts of the CHORUS reference pilot use it. It is an engineering prerequisite and is not written (NP1.7).
  - **Where the run limits stand.** With the four protected files the owner approved (D139), the instruction's recorder command carries `--render-spec-json`, whose value embeds the raw runtime declaration, and that declaration contains `deadline_seconds` and `budget_guard_usd` (`api_runner.py:1194–1211`; `native_shared_render.py:205–212`, `:289–295`, `:378–380`; `native_shared_runtime_constants.py:8–9`; read by the lead at `6561dac3c3af50cbfce1ba3c8b6ad21d9cd4b834`). The lead decided to pass the render specification through the controller's environment before the canary (#6065), which takes it out of the recorder line. The gate depends on neither: the limit set is a registered value, so the canary's registration, which declares amendment N1's set, is never equal to a production registration.
- **The rule** [proposed, NP1.10(s)]. It is the plan's floor rule (§8, lines 1125–1127) read for native pilots, and it takes no value from the API arm:

> The registered native coverage floor is the lowest of the eligible native pilots' D37 at-receipt coverage fractions, `with_receipt_at_receipt / receiptable_at_receipt`, rounded down to a multiple of 1/20 and capped at 19/20.

  - **Eligible pilots:** the reference run, which is the first accepted attempt of the CHORUS reference pilot (above), and, if NP1.10(e) is yes and AI_READI is in scope, the AI_READI native pilot. **The canary's reading is reported and is never an input;** that supersedes D109's clause quoted above. Only an accepted attempt's saved result supplies a fraction; a rejected, stopped or assisted attempt never does (lines 1129–1133).
  - **Which reading: one.** Each pilot contributes one fraction, from the `slots` of its final-stage receipt check: the block the controller writes with `native_receipt_stage: final` (`native_shared_receipts.py:484–498`), read from the accepted attempt's saved result.
  - **The second reading is a check, never an input.** On the at-receipt basis the receipt-completion stage's `after` block is the checker run on the sealed original with the completed receipt (`:433–437`), so it should equal the final-stage pair. It is reported beside it. If the two differ, that is an instrument defect: it is filed as a finding, and the floor is not registered while it is unresolved. The floor's registration never chooses between two observed ratios. **The check applies on the at-receipt basis only.** On the final-record basis the two readings differ by design: the completion stage's `after` block reads the phase-1 record, and the gated ratio reads the final record.
  - **Readings that are not used.** The controller also evaluates the floor at the initial receipt check, where it forces the state to pending (`:363–364`). That is reported. It does not enter the rule and does not gate a production record. Final-record coverage is reported for every record as the plan's descriptive quantity.
  - **What gates in production:** the final-stage check's reading on the chosen basis, against the registered fraction (above, and NP1.6).
  - **An accepted pilot whose saved result has no such reading** supplies no fraction. Its project stays in scope, and the floor is not registered (below).
  - **Arithmetic:** exact integers, `floor(20 × with_receipt_at_receipt / receiptable_at_receipt) / 20`, then the minimum with 19/20, registered as a numerator over the denominator 20.
  - **Why the cap:** the plan's reason (lines 1134–1140). Receipt completion drives the at-receipt ratio towards 1, and a floor of 1 would stop a replicate on one unreceipted leaf.
  - **The lowest value that can be registered is 1/20.** The plan's rule rests on a re-canary that has passed its own 19/20 gate (lines 1147–1149). The native canary is ungated (D109), so the native floor is wholly the pilots' own reading. A low reading registers a low floor, which gates little. The value is reported with that said, and every production record's coverage is reported whatever the floor. A reading under 1/20 cannot be registered: the pilot's project stays in scope, and the floor is not registered (below).
  - **The AI_READI branch.** NP1.6's table says how the pilot concludes. While it is pending the floor waits (below). If it concludes without acceptance for a cause that is not rule-level, AI_READI leaves scope as infeasible, reported as a feasibility result, and the CHORUS reference run alone sets the value (plan step 8, lines 307–312). A rule-level rejection is NP1.6's case. An accepted AI_READI pilot never takes AI_READI out of scope, whatever its reading.
  - **When the floor is not registered.** In each of these cases no production cell registers, and no other observed ratio is substituted (lines 1150–1152):
    - **a required pilot is still pending,** or waits on an instrument or unknown case (NP1.6): the floor waits for it;
    - **an instrument finding on the two readings is open:** the floor waits until it is resolved;
    - **an accepted pilot has no usable fraction:** its saved result has no final-stage reading, its denominator is zero, or its reading is under 1/20. Its project stays in scope. A prospective amendment, reviewed as this one, says how the floor is set; it is under the bar, which says what it may apply (above);
    - **there is no reference run,** because the CHORUS reference pilot concluded without acceptance (NP1.6): a prospective amendment says how the condition proceeds;
    - **the gate's result for the AI_READI pilot's registration is "cannot decide":** that registration waits, and so does the floor;
    - **the reference run's source no longer saves the fields this rule reads:** the floor waits for a prospective amendment that restates them (below).

    An AI_READI pilot that concludes without acceptance for a cause that is not rule-level is not one of these cases: AI_READI leaves scope, and the CHORUS reference run alone sets the value.
  - **Conformance, not choice.** The floor's registration confirms from the reference run's source that these are still the fields. If they are not, the floor is not registered until a prospective amendment restates it.
- **How the value is registered** [proposed, NP1.10(z)]: in a dated amendment that gets this amendment's review and the owner's ratification. It checks the arithmetic and the inputs and does not revisit the rule (lines 1159–1163).
