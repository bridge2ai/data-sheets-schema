# Semantic exchange and RO-Crate conformance review

Reviewed 2026-11-10 at frozen main `7233f193ad102a8488b31ec7333662c8fefaa996`.

**Verdict: D4D retains an explicit semantic exchange vocabulary and several functioning, bounded conversion routes. The current evidence does not support “fully compliant” or “lossless Core ↔ RO-Crate.”** Some limits are deliberate and accurately reported; other public claims exceed the implementation. A small offline export also demonstrates concrete preservation and RO-Crate conformance gaps.

This review is independent of schema-history and AI-readiness criterion reviews. It changes no schema, converter, mapping or test. Links below pin the reviewed commit rather than moving main. Existing issue associations were checked by the lead; no issues were created by this worker.

## What the current contract actually comprises

| Layer | Current evidence | What it establishes |
| --- | --- | --- |
| Vocabulary alignment | Canonical SKOS TTL; comprehensive label and URI SSSOM tables | Relations between names/URIs; not executable bidirectional structural transformations |
| Structural mapping | 165 committed SSSOM rows; generator produces 155, with known curated exceptions | Selected ranges/cardinalities and mapping strategies; regeneration is deliberately incomplete |
| Core schema | `CoreDataset`, `CoreDistribution`, `CoreDatasetCollection` plus imported classes | A selected exchange surface, including structured objects; existence of a slot does not prove that a converter carries it |
| Full → Core | `linkml_mappings/full-to-core-mapping.yaml` | Projection from full D4D to Core, including files/collections into distributions; this is a different operation from Core ↔ RO-Crate |
| Static RO-Crate → D4D | `rocrate_map.py` with `d4d_rocrate_interface_mapping.tsv` | Root-aware placement into full-schema `Dataset`, declared dispositions and assertion evidence; explicitly not scientific coverage or a measured lossless inverse |
| FAIRSCAPE converters | Hand-written forward and reverse converters, with finite projection/evidence contracts | Operational conversion for selected structures; Pydantic model validity and JSON readback; scoped omission reports |
| Unified transformation/validation | Legacy `transform_api.py` and `unified_validator.py` | Forward-to-RO-Crate and round-trip operations remain unfinished; SHACL validation remains a stub |

The forward converter explicitly emits RO-Crate **1.2**, using the FAIRSCAPE submodule pinned at `8c80311d7d8b0fadac07dca9567d632103691f48`; the observed model version is **1.0.24**. It uses `https://w3id.org/EVI#` and `http://mlcommons.org/croissant/RAI/`. The exchange documentation limits RAI targets to the 20 properties in RAI 1.0. A generic claim of alignment with the newest RO-Crate release would need a separate assessment; this review checks the implementation's declared 1.2 target.

Sources: [exchange artifacts and rules](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/docs/semantic_exchange.md#L13-L82), [Core definitions](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Core.yaml#L1-L175), [full-to-core specification](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/linkml_mappings/full-to-core-mapping.yaml), [static mapper contract](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/rocrate_map.py#L1-L43), [export target and context](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/fairscape_integration/d4d_to_fairscape.py#L122-L148).

The reverse FAIRSCAPE converter explicitly says its mappings are extraction code. Its old SSSOM constructor argument was removed because the loaded table did not affect output. Therefore updating a canonical mapping table does not itself update this conversion route. The separate LinkML-Map helper is not evidence that the FAIRSCAPE converter executes the canonical SSSOM. [Reverse converter implementation note](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/fairscape_integration/fairscape_to_d4d.py#L526-L537).

## Measured vocabulary coverage and schema drift

The saved [static census](exchange_static.json) independently reproduces the documented **301** comprehensive rows, **165** structural rows, and **150** SKOS mapping triples. Comprehensive row statuses are:

| Status | Rows |
| --- | ---: |
| mapped | 176 |
| unmapped | 84 |
| novel_d4d | 27 |
| free_text | 13 |
| recommended | 1 |

These are **one row per schema slot name**, not one row per class/slot/range combination, nor a count of fully preserved runtime fields. Even a `mapped` row can encode a broad or partial semantic relation. The separate URI table's high rate of declared URIs includes local D4D terms: it must not be reported as equally high external-vocabulary coverage. SSSOM's `NoTermFound` sentinel is an explicit no-match, even though its representation includes `skos:exactMatch`.

Using `SchemaView.class_induced_slots` on the current Core module gives **84 CoreDataset slots**, **17 CoreDistribution slots**, and **27 CoreDatasetCollection slots**, including inherited slots. These denominators are not interchangeable with historical approximate field counts or unique global slot-name counts.

The comprehensive table deliberately inventories the full schema. A Core-specific slot such as `distributions` is absent from that table even though Core gives it `dcat:distribution`; absence here is not absence of a schema annotation. Conversely, Core still contains `addressing_gaps`, `anomalies`, `content_warnings`, `human_subject_research`, `informed_consent`, `at_risk_populations` and `data_governance`, whose name-matched comprehensive rows explicitly have no external match. This conflicts with the current documentation's blanket claim that **every Core slot is aligned through the canonical SKOS exchange layer**. It does not establish that these Core definitions have no mapping annotations: some still carry local or other annotations. The mismatch is between the canonical alignment contract and that blanket claim, and must not be reduced to a name-joined table being a complete Core annotation inventory. Some former self-mappings were correctly withdrawn rather than being genuine loss of interoperability: the TTL explains why local D4D targets were removed. [Core claims](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/docs/d4d_core.md#L3-L53), [withdrawn self-alignments](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/semantic_exchange/d4d_rocrate_skos_alignment.ttl#L255-L263).

Two particularly consequential unresolved mappings are visible in source: `conforms_to` aligns to `schema:conformsTo`, whereas the schema correctly uses `dcterms:conformsTo`; and generic `hash` has `skos:exactMatch evi:md5`. Generic algorithm-qualified hashes cannot safely be assumed to be MD5. The comprehensive table marks the latter TTL/schema disagreement as open. `id → rdf:ID` is also explicitly recorded as an open disagreement. These are term-level concerns independent of converter functionality. [TTL assertions](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/semantic_exchange/d4d_rocrate_skos_alignment.ttl#L234-L252), [correct schema conformance slot](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Base_import.yaml#L491-L522), [identity disagreement documentation](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/docs/semantic_exchange.md#L75-L82).

Two additional current schema defects are already tracked:

- **Core annotations still use invalid RAI targets (#3972).** `imputation_protocols` names `rai:imputationProtocol`, whereas the canonical TTL now uses `rai:dataImputationProtocol`. Core also retains `rai:prohibitedUses` on both discouraged and prohibited uses, `rai:ethicalReview` on ethical reviews, and `rai:confidentialityLevel` on deidentification. The canonical TTL explicitly removed these latter targets because they are not Croissant RAI 1.0 properties; access classification is also not equivalent to deidentification. This is actual disagreement between current schema annotations and the maintained canonical layer. [Core imputation](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Core.yaml#L408-L416), [use annotations](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Core.yaml#L477-L505), [ethics annotation](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Core.yaml#L584-L592), [deidentification annotation](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Core.yaml#L682-L689), [canonical removals](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/semantic_exchange/d4d_rocrate_skos_alignment.ttl#L282-L289), [canonical imputation correction](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/semantic_exchange/d4d_rocrate_skos_alignment.ttl#L320-L322).
- **Full Dataset is typed as a distribution (#4034).** Its `class_uri` is `dcat:Distribution` and its exact mapping is `schema:DataDownload`, while CoreDataset is typed `dcat:Dataset` and mapped to `schema:Dataset`. This changes RDF class interpretation across the full/Core boundary and needs an explicit modeling decision; YAML shape validation alone cannot settle it. [Full Dataset class](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/data_sheets_schema.yaml#L136-L147), [CoreDataset class](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Core.yaml#L134-L148).

## Bounded operational canary

The offline diagnostic recorded **0.668 seconds** of combined elapsed time through imports, static census, one forward API conversion, RDF parsing and model validation; this is **not a conversion-only timing**. It stayed below its 30-second cap, used the frozen converter and existing matching FAIRSCAPE submodule, and made no provider/network calls. The initial attempt stopped at an artifact-write sandbox denial before conversion; the authorized scoped retry produced both non-empty JSON evidence files. No broad tests ran.

The small fictional input contains a structured Creator with a Person, one known limitation, and one CoreDistribution identifying CSV serialization and BIDS conformance. Initially its shapes were inspected against source. The lead subsequently validated **the same exact saved input successfully** against JSON Schema generated from the pinned Core module with `top_class=CoreDataset`. That separate 1.307-second check also accepted an id-only record and rejected `{}` for missing required `id`. It used LinkML 1.9.3, linkml-runtime 1.9.4 and jsonschema 4.25.1's `Draft201909Validator`. [Later input-validation evidence](validation_core.json), [validation helper](../../scripts/adhoc/schema_review_validation_20261110.py).

The later validation did **not** rerun the converter or validate RO-Crate conformance. The original canary exercises the generic forward API, not a separately established Core-specific CLI workflow. Consequently, Core distribution omission demonstrates an unsupported-route boundary relative to the public lossless-Core claim; it does not establish a regression in a previously supported Core converter.

| Observation | Result | Interpretation |
| --- | --- | --- |
| Genuine FAIRSCAPE model and exact JSON readback | `model_valid: true` | The supported model path works |
| `known_limitations[0].limitation_description` | Text survives as `rai:dataLimitations` | A documented narrative projection works; the source object shape is not preserved |
| Creator's `principal_investigator.name` | Exported `author` is `Unknown` | The exporter reads the wrapper's `name`, not the Person in the current Creator structure |
| Core `distributions` including BIDS | No distribution emitted; `hasPart: []`; BIDS absent | The exporter builds `file_collections`; this demonstrates an unsupported Core-route boundary, not a proven historical regression |
| Original dataset `id` | Absent from wire; root is `./` | Local root identification is legal, but source identity is not retained elsewhere in this output |
| Publication date | No `datePublished` | Pydantic-valid output fails a required RO-Crate 1.2 root property |
| Descriptor `conformsTo`, expanded by RDFLib | `https://schema.org/conformsTo` | The emitted context gives the conformance assertion the wrong predicate |
| Projection summary | `incomplete: false` | This status is explicitly scoped to 15 fields; it does not account for creator/distribution/identity losses |

Evidence: [full input, output, model identity and checks](exchange_canary.json); [reproduction helper](../../scripts/adhoc/schema_exchange_review_20261110.py). Runtime imports are recorded, so the canary cannot silently be mistaken for a test of the dirty primary checkout. The only primary-checkout code dependency is the unchanged matching FAIRSCAPE submodule.

The creator behavior follows [the current `name` extraction](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/fairscape_integration/d4d_to_fairscape.py#L175-L190), whereas the current schema uses [Creator.principal_investigator → Person](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Motivation.yaml#L86-L126). Export constructs `file_collections` and optional dates in [the dataset builder](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/fairscape_integration/d4d_to_fairscape.py#L197-L227). Core deliberately uses [distributions](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/data_sheets_schema/schema/D4D_Core.yaml#L158-L174).

RO-Crate 1.2 requires a root `datePublished` string. Its JSON-LD documentation permits an embedded context, but maps `conformsTo` to the Dublin Core predicate. The problem is the emitted predicate, not the mere use of an inline context. [RO-Crate 1.2 root requirements](https://www.researchobject.org/ro-crate/specification/1.2/root-data-entity.html#direct-properties-of-the-root-data-entity), [embedded-context semantics](https://www.researchobject.org/ro-crate/specification/1.2/appendix/jsonld.html#ro-crate-json-ld-context).

## Preservation and validation claims that need narrowing

1. **Lossless round-trip is not demonstrated.** The Core guide explicitly calls Core ↔ RO-Crate lossless, while the unified API raises `NotImplementedError` for D4D → RO-Crate and its round-trip test. Separate FAIRSCAPE forward and reverse converters do exist, so “there is no reverse implementation” would be false. What is missing is a defined supported round-trip contract and evidence that these independently implemented paths meet it. [Core claim](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/docs/d4d_core.md#L53), [unified export stub](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/transformation/transform_api.py#L499-L522), [round-trip stub](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/transformation/transform_api.py#L693-L711).

2. **Some current projections are intentionally lossy and honest about it.** Fifteen forward fields accept only a narrowly defined narrative object or legacy scalar compatibility shape. Extra object members, identifiers, multiple scalar-target entries or unsupported units can be omitted, with scoped evidence/warnings. This is a useful improvement, not a reopened claim that the earlier schema-valid-object fix failed. Model validity, successful serialization and preservation of selected text are distinct from retaining the full source object, source semantics or inverse reconstruction. [Current finite-projection contract](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/docs/fairscape_forward_types.md#L1-L81).

3. **A validation pass can still mean an unimplemented check.** The unified RO-Crate semantic validator returns without running SHACL; it either warns that pyshacl is missing or states the SHACL check is a stub. `validate_roundtrip` creates a report with `passed=True`, adds a not-implemented warning and returns it. Callers must not interpret that Boolean as conformance or preservation. The `complete` profile is more careful: its requirements are undefined and it is reported unavailable. [SHACL stub](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/validation/unified_validator.py#L484-L501), [round-trip success-shaped stub](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/validation/unified_validator.py#L642-L671), [unavailable complete profile](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/src/validation/unified_validator.py#L577-L590).

4. **Historical coverage statements are not current acceptance results.** The March implementation summary reports historical counts and estimates, and carries a later notice limiting the legacy publication contract to closed Dataset output with sidecars. It also acknowledges unfinished reverse and SHACL work. It should not override current source or be cited as proof of 85–95% measured round-trip preservation. [Historical summary and caveat](https://github.com/bridge2ai/data-sheets-schema/blob/7233f193ad102a8488b31ec7333662c8fefaa996/notes/SEMANTIC_EXCHANGE_IMPLEMENTATION.md).

A cheap development sequence is sufficient to make progress:

1. Publish a matrix naming the supported route, input class, profile, target version, required metadata and declared losses; correct the blanket Core claims.
2. Add a tiny synthetic fixture for each supported boundary, validating the input against its actual class. Check output RDF predicates and RO-Crate required fields separately from the FAIRSCAPE Pydantic model. Keep richer Creator, distribution-standard and multi-entry governance examples.
3. Fix context/required-root handling and preserve structured identity/creators/distributions, or refuse unsupported classes and structures with explicit evidence. Retain the finite projection protections already implemented.
4. Compare accepted outputs in the inverse direction under a declared equivalence rule: exact identity/cardinality/types where promised, documented transformations elsewhere. Include negative tests that must be refused, not merely a happy path.
5. Run canonical mapping drift checks and affected cohorts only after the tiny fixture passes. A successful mapping regeneration or schema validation is not a substitute for this end-to-end exchange check.

The present review establishes that the mapping vocabulary remains maintained and several real conversions work. It also establishes that a current FAIRSCAPE-model-valid export can lose current structured content and fail the declared RO-Crate 1.2 contract. Full exchange compliance should remain unclaimed until the scoped acceptance work above passes.
