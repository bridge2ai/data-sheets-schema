# D4D schema alignment with the AI-readiness preprint

Review date: 2026-11-10. Schema snapshot: `7233f193ad102a8488b31ec7333662c8fefaa996` (remote main), declaring version 3.2.0. This is a review of schema representation, not an assessment of a generated datasheet or a dataset release. This component review changed no schema and made no model calls. The lead's separately executed, bounded full/Core shape-validation checks are incorporated below; no additional tests were run for this revision.

The current schema broadly supports the paper's subject matter, but **“still fully aligned” is not established**. The full schema has meaningful structured support across the framework, with important gaps and many evidence-bearing values remaining prose. CoreDataset additionally excludes some relevant full-schema structures. Schema validation does not require evidence for every criterion and does not verify the truth of supplied claims. The earlier mapping cannot establish a historical state of full alignment.

The cited PMID now resolves to *AI-readiness Criteria for Biomedical Data*, bioRxiv version 6, dated April 24, 2026. Its Table 1 has **28 subcriteria across seven dimensions**, with counts 4 + 4 + 5 + 3 + 4 + 4 + 4. The paper presents readiness as context-dependent and multidimensional; metadata capability alone does not certify a dataset. This review uses the current version, not the version 4 PDF cited by the repository's December 2025 mapping. [PubMed](https://pubmed.ncbi.nlm.nih.gov/39484409/), [current full text and Table 1](https://pmc.ncbi.nlm.nih.gov/articles/PMC11526931/#T1), [version 6](https://www.biorxiv.org/content/10.1101/2024.10.23.619844v6).

## How to read the matrix

IDs are those of Table 1. The short topics below are review labels, not a reproduction of its practices. **S** means directly addressable structured metadata; values can still include prose. **P** means a material part is expressible only indirectly, as prose, or with incomplete structure. **N** means no dedicated typed representation was found in the reviewed schema closure. These are representation judgments, not readiness scores. No percentage of “full compliance” is calculated.

Paths in the matrix are class/slot paths. Source anchors refer to `src/data_sheets_schema/schema/` at the pinned commit. `Dataset` and `CoreDataset` inherit `Information` and `NamedThing`. `DatasetProperty` contributes common descriptive fields and `used_software`; a child class need not redeclare these. “Both” means both full and Core expose the stated route. Imported class definitions alone do not make that class reachable through a dataset attribute.

## Validation boundary

`NamedThing.id` has `identifier: true` at `D4D_Base_import.yaml:95`. Both dataset classes inherit it. The generated Python model explicitly rejects an empty id (`src/data_sheets_schema/datamodel/data_sheets_schema.py:162`). Therefore, “there are no required fields” would be inaccurate.

However, the top-level evidence attributes of Dataset and CoreDataset are optional. Nested requirements apply only when their enclosing objects are supplied: for example, `VariableMetadata.variable_name` and `RawDataSource.source_description`. None of these requirements says that every AI-readiness criterion must have evidence.

The lead's [Core validation evidence](validation_core.json) and [full validation evidence](validation_full.json), produced by [the bounded validation helper](../../scripts/adhoc/schema_review_validation_20261110.py), confirm this boundary for both `CoreDataset` and `Dataset`: an id-only record passes and an empty object fails because `id` is required. The original exchange-canary input passes Core validation; the same input with only `distributions` removed passes full validation, retaining its structured Creator/Person and limitation object.

Each invocation generated JSON Schema in memory from the pinned schema source, using LinkML 1.9.3, linkml-runtime 1.9.4 and jsonschema 4.25.1 with `Draft201909Validator`. Recorded elapsed times are 1.307 seconds for Core and 1.390 seconds for full. These checks establish shape validity for the tested inputs only; they perform no semantic, scientific-evidence, endpoint, AI-readiness or RO-Crate conformance checks and do not rerun the converter. The full input is a distinct shape-validation control, not a second conversion result.

Three different questions need different checks:

1. Can a record conform to the metadata schema? Existing type/shape validation answers this.
2. Does it contain sufficient, supported evidence for each applicable criterion? A criterion-aware assessment profile must answer this, with explicit unknown and not-applicable states.
3. Are the dataset and its release practices actually compliant? This requires examining artifacts, repositories, endpoint behavior, approvals, provenance and operating practices.

Generation/run telemetry schemas record production of the datasheet. They must not be counted as the documented dataset's transformation provenance or quality evidence without a demonstrated connection.

## Problems in the existing alignment documentation

`notes/AI-Readiness/D4D_AI_READINESS_MAPPING.md` is dated 2025-12-12 and cites a version 4 PDF. Its summary matrix at lines 819–852 has 28 rows, including six marked partial, while lines 856–858 report 22/26 full and 4/26 partial. That arithmetic is internally inconsistent even before assessing whether the mappings are correct.

Several of its asserted identifiers do not exist in the current imported schema: `AccessMethod`, `LandingPage`, `DataSource`, `OriginalDataSource`, `DataSplit`, `HashAlgorithmEnum`, `Software.software_name`, and `PreprocessingStrategy.preprocessing_description`. Current alternatives have different paths and semantics: `RawDataSource`, `Splits.split_details`, inherited `Software.name`, `Software.url`, `PreprocessingStrategy.preprocessing_details`, and `File.sha256`. Some old descriptions also understate improvements, especially the current DataGovernance object. Conversely, the real `VariableMetadata.missing_value_code` should not be reported as missing.

These are defects in a purported precise crosswalk, not evidence that all those features once existed and were removed. Historical removal would require an independent commit-level comparison.

Search completeness: schema absence statements above use an ignore-independent search (`rg -uu`) over `src/data_sheets_schema/schema/` in the clean pinned review worktree, plus direct inspection of Dataset/Core imports and attribute declarations. This includes generated merged schemas and unrelated generation/telemetry schemas, which were separated by scope. It is not a claim that no ignored historical draft anywhere on disk contains those concepts.

## Recommended order of work

1. **Correct the assurance documentation.** Replace the invalid denominator and stale paths with this pinned, criterion-indexed crosswalk. Keep the historical document as a dated artifact or mark it superseded; do not silently present it as current. Do not issue a replacement global coverage percentage.
2. **Define an assessment profile before expanding the schema.** Record criterion ID, applicable scope, evidence references, assessment status, rationale, assessed release and assessor. Separate record completeness from source-supported evidence and independently checked operations. This can complement the existing schemas without making sparse legacy metadata invalid.
3. **Make the Core boundary explicit.** Decide whether Core alone is intended to carry readiness evidence. If so, prioritize variable dictionaries, split context and privacy details, with explicit mappings. If Core is a bounded exchange projection, require a linked full record/evidence package and state the losses rather than declaring parity.
4. **Reuse external evidence representations where possible.** Provenance, data dictionaries, validation reports, software artifacts and environment specifications can be linked using typed relationships; adding six bespoke classes is not automatically the right solution. Prioritize a generic QC result/report link, statistical summaries distinct from permitted bounds, and runtime requirements where applicable.
5. **Verify one representative release end to end.** Use one full/Core pair with variable metadata, a split, a privacy statement, a raw-to-processed relationship and a checksum. Establish which facts survive exchange and which are intentionally external. Validate shape, inspect supporting evidence, and separately verify packaging/endpoint behavior before a corpus-wide claim.

Uncertainty remains about actual dataset evidence quality, hosted metadata persistence, live service behavior, paper-version changes before v6, and converter semantics. Those are not resolved by this schema-only review. The lead's historical and semantic-exchange reports should be read alongside this matrix before deciding whether a discrepancy is a schema regression, a deliberate Core projection, stale documentation, or an operational gap.
