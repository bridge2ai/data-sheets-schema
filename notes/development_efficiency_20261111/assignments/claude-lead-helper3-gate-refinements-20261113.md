# Assignment to Codex helper 3: three refinements to the manifest and the gate, from the review of the amendment's draft v10

From the Claude lead, 2026-11-13. Short names and rules are in `claude-lead-helper-context-20261112.md` beside this file. This comes after `claude-lead-helper3-environment-manifest-ruling-20261113.md`. If you are still in that assignment when you read this, apply these in the same work.

A Codex CLI review of the production amendment's draft v10 (`E/plans/reviews/np1v10_2f5c6679_codex_review_2026-11-13.md`, findings P2-2, P2-3, P2-4) found three things the gate and the manifest must do. The lead's rulings:

1. **The manifest verifies installed contents, not only `RECORD` bytes** (P2-4). When the manifest is generated, at preparation and again at dispatch, every file a third-party distribution's `RECORD` lists with a hash is read and checked against that hash; a mismatch, a missing file or an unreadable file holds. Entries `RECORD` lists without a hash (the `RECORD` file itself, compiled `.pyc` files) are named in the manifest as unverified by kind, with their count. An editable or development install of a third-party distribution holds. The project's own package is covered by the source pins and is not part of the manifest.
2. **Paths: the stratum's registrations share the reference's checkout path and interpreter path** (P2-3). The existing validators reconstruct the working directory and the interpreter path and version from the validating process and compare the whole preparation body, so a candidate built in another checkout cannot validate under the reference export. Rather than teach them path substitution, the gate treats the checkout path and the interpreter path as **must-equal**; only the per-attempt roots (attempt, evidence, output, stage) and the registration, instruction and probe file paths stay per-run. Say in the data file which paths are which, and show that the validators then pass for a candidate registered from the same checkout.
3. **The demonstration covers every branch the amendment relies on** (P2-2), on the final registration format, with a machine-checkable field-coverage inventory (every leaf of every recorded document, including embedded JSON documents and variable-key collections, classified; a whole embedded document classified as derived must not hide a scientific leaf value from the must-equal check). Cases, each with its expected result:
   - equal: a packet against itself; against the same project's later registration; against another project's registration with that project's tuple; **a valid pending-to-registered floor transition**; a reference whose 14-day validity has passed;
   - not equal: a changed prompt asset, binary hash, bound, interpreter version, a third-party distribution's version or installed file, a wrong floor value or basis, **an internally valid registration with the wrong project tuple**; and a mixed case of two prohibited differences, which lists both;
   - cannot decide: a missing artifact, an unknown field, an incorrect derived binding, and invalid evidence; and a mixed case of a prohibited difference with invalid evidence, whose result follows the precedence the data file states (state it: a prohibited difference in a must-equal pin is decided first only when its pin is valid; invalid or unclassified evidence anywhere otherwise holds).
   Repeat the demonstration whenever a pre-reference repair changes the registration format.
