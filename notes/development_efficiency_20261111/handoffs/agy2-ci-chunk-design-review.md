## Question 1: Fixture Multiplication & What Cross-Shard Splitting Adds Beyond Intra-Shard `xdist`

### Finding 1 — Intra-shard `xdist` (`--dist load --maxschedchunk=1`) vs. cross-shard chunking (`utils/pytest_shard.py:194-200`, `.github/workflows/main.yaml:303-305`)

- **Evidence**:
  - `.github/workflows/main.yaml:303-305` and `utils/ci_sharding.md:27-35`: each ordinary shard already runs `pytest -n logical --maxprocesses=4 --dist load --maxschedchunk=1`.
  - `utils/pytest_shard.py:194-200`: within each shard, collected items are stably sorted by `-estimates[path] / counts[path]` so files with the highest average duration per item start first and `xdist` hands out individual items one at a time (`--maxschedchunk=1`) across the 4 workers (`gw0`..`gw3`).
  - `notes/development_efficiency_20261111/handoffs/agy1-ci-result.md:25-32`: in post-refresh run `42947560899`, the ratio of summed overlapping testcase durations to `testsuite` wall time (`actual_case_s / suite_wall_s`) was **`3.701` to `3.848` out of `4.0` workers** across all 8 shards (`3.819` in Shard 1 with `tests/test_report_admission.py`; `3.843` in Shard 8).
- **What cross-shard splitting adds vs. what it costs**:
  - Within a single shard, `xdist --dist load --maxschedchunk=1` can parallelize a multi-item file across at most **4 workers** (`--maxprocesses=4`). Cross-shard splitting into `k` chunks allows items from a single file (such as `tests/test_report_admission.py`, `5162.752s` across 32 items, max single item `768.0s`) to run on more than 4 workers concurrently across different runner VMs.
  - **However**, cross-shard splitting only helps wall time when a single file's total case-seconds divided by 4 (`5162.8s / 4 = 1290.7s`) exceeds the per-shard target (`6389.9s / 4 = 1597.5s` for 8 shards; `8519.9s / 4 = 2130.0s` for 6 shards) **or** prevents the file from packing cleanly into `6389.9s` shard buckets. Here, **not a single file in the repository exceeds `6389.9s`**, and file-level packing already achieves a `0.002s` spread across 8 shards and a `0.004s` spread across 6 shards.
  - Conversely, while a `scope="module"` fixture, `setUpClass` hook, or module-level `lru_cache` inside 1 shard can be evaluated in at most $\min(4, m)$ worker processes (where $m$ is the number of items using that fixture/cache), splitting those $m$ items across $C$ shards multiplies the setup across up to $\sum_{j=1}^{C} \min(4, m_j)$ worker processes across $C$ shards (up to $4C$ processes total) and places that cold-start setup latency on the critical path of every shard receiving a chunk.

## Question 3: Determinism Across Shards

### Finding 4 — Collection order, `_estimates` median fallback, and intra-shard sort (`utils/pytest_shard.py:144-200`)

- **Evidence**:
  - **Parametrize IDs and collection order across `tests/`**:
    - AST audit of all `pytest.mark.parametrize` and `pytest.fixture(params=...)` decorators across `tests/` confirms that parameter lists use deterministic literals, tuples/lists, or `sorted(...)` (e.g. `tests/test_provenance_reasoning_message.py:350` uses `params=sorted(BAD_LINES)`). No test file embeds timestamps, `tmp_path`, or unsorted filesystem globs in parametrize IDs at collection time.
    - Within `unittest.TestCase` subclasses, pytest's `UnitTestCase.collect` uses `unittest.TestLoader.getTestCaseNames` (alphabetical by method name); for module-level functions and plain pytest classes, pytest collects in AST definition order.
    - **However**, `tests/test_ci_sharding.py:140-144` (`test_measured_partition_is_order_independent_and_reduces_estimated_imbalance`) explicitly requires that reversing the input order of files does not change the shard assignment (`assert assigned == balanced_files(reversed(list(weights)), 8, weights)`). If a pure nodeid-chunking function chunks in whatever file order `nodeids` is passed without first grouping items by canonical file path `nodeid.split("::", 1)[0]` and sorting files canonically, reversing the file order would change tie-breaking!
  - **The fallback median trap in `_estimates(paths, weights)` (`utils/pytest_shard.py:144-149`)**:
    - `utils/pytest_shard.py:144-148` computes `known = [weights[path] for path in paths if path in weights]` over `paths = set(paths)` and sets `fallback = median(known) if known else 1.0`.
    - If a file with weight $w > \text{CHUNK\_THRESHOLD}$ were expanded into $k$ entries of weight $w / k$ *before* computing `median(known)`, the median of `known` would shift whenever a file is chunked, altering the fallback weight assigned to untimed files. Therefore, `_estimates` **must** compute file-level estimates over the set of distinct file paths first, and only then split multi-item files whose file estimate $w$ exceeds `CHUNK_THRESHOLD`.
  - **Remainder item distribution when $n \not\equiv 0 \pmod k$ and greedy tie-breaking**:
    - When a file of $n$ items and weight $w$ is split into $k$ chunks, $(n \bmod k)$ chunks have $\lceil n/k \rceil$ items and $k - (n \bmod k)$ chunks have $\lfloor n/k \rfloor$ items (e.g. `start = (idx * n) // k`, `end = ((idx + 1) * n) // k` for `idx in range(k)`).
    - Because all $k$ chunks of a file have the exact same weight `w / k` (under `AGY1`'s proposal), greedy bin-packing (`utils/pytest_shard.py:156-160`) must sort scheduling units by `(-unit_weight, file_path, chunk_index)` and break shard ties by `(loads[shard_idx], counts[shard_idx], shard_idx)` so that every shard independently assigns `(file_path, chunk_index)` to the exact same owner shard.

### Finding 5 — Duplicate `item.nodeid` collisions (`#4520` / `#5020`) break both `dict[nodeid, shard]` and `utils/update_ci_shard_timings.py:38-39`

  - `utils/update_ci_shard_timings.py:37-42` (tested by `tests/test_ci_timing_update.py:62-67`, `test_same_label_in_different_artifacts_is_rejected`) enforces:

- **Why `AGY1`'s proposed pure function signature is a trap**:
  - `claude-lead-agy1-ci-chunk-sharding.md:30-31` specifies: *"Factor the chunk builder as a pure function that maps the collected ordinary node ids, a shard total and the weights to an owner shard per node id"*.

- **Smallest Design Constraint (Question 3)**:
  - Before computing intra-file chunks, the pure function **must** group items by `(file_path, distinct_nodeid)` in first-seen intra-file order (so all occurrences of any duplicate `nodeid` belong to the same atomic item group and can never be separated across a chunk boundary), and must group files by canonical `file_path = nodeid.split("::", 1)[0]`, compute `_estimates` on distinct `file_path`s first, and sort chunks by `(-chunk_weight, file_path, chunk_index)`.
