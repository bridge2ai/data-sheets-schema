# Historical merged records — investigation evidence

These July 2026 outputs are retained as evidence for the coverage-merge
investigation in [#176](https://github.com/bridge2ai/data-sheets-schema/issues/176).
They are not an approval to ship merged datasheets. The four guarded merges have
`record_mode: derived` provenance in
[`claudecode_agent_merged_core/2026-07-29_guarded-union/`](../claudecode_agent_merged_core/2026-07-29_guarded-union/).
The unguarded CM4AI example below has no provenance and is knowingly incoherent.

Produced 2026-07-29 from the three generic baseline replicates
(`2026-07-28_claude-opus-5-generic_rep{1,2,3}`) by
`src/data_sheets_schema/merge.py`.

## Provenance exists; shipping policy remains open

Derived provenance names contributing records by hash and records the combination
rule and source contributions. The playbook already has an explicit derivation
carve-out; the immutable v2 text is in
["The one exception: derivation, which is not generation"](../../../.claude/commands/d4d-full-core-v2.md#the-one-exception-derivation-which-is-not-generation).
These mechanisms disclose how a merge was made. They do not certify scientific
correctness or shipping eligibility.

[#4765](https://github.com/bridge2ai/data-sheets-schema/issues/4765) still requires
a recorded choice: keep merges as investigation artifacts with selection as the
shipping route, or support merged outputs under stated conditions. If merges are
to ship, that issue also requires current-arm scoring under a pinned instrument,
replay over pinned source bytes, current-schema validation, a derived core, and
pair checks. The historical measurements below do not satisfy those obligations.
The current-arm evaluation and fitness feedback work remain pending; this README
records no calibration acceptance or provider-campaign authorization.

## `2026-07-29_coverage-union/` — unguarded, CM4AI is incoherent

Kept because it demonstrates the failure mode. The CM4AI record says:

    title    Cell Maps for Artificial Intelligence (CM4AI) Data Release Programme
    version  June 2026 Data Release (Beta); Dataverse dataset version 2.0
    issued   2026-06-17T00:00:00Z
    doi      doi:10.18130/V3/HIGT4C

The title came from rep3, which describes the release *programme*. The version,
issue date and DOI came from rep2, which describes one release inside it. The
record documents neither subject.

**It passes `linkml-validate`.** That is the point of keeping it: schema
validation cannot detect a spliced referent, so a separate coherence check is
required and no amount of stricter validation substitutes.

`union_merge(guarded=False)` now raises on records like these rather than
writing them, so this directory cannot be regenerated by the current code.

## `2026-07-29_guarded-union/` — referent guard applied

Every referent-bearing field comes from one base record; identities the base
never asserted are dropped rather than imported.

The original investigation reported that all four validated against the
then-current `Dataset` schema. This is a historical result, not a current-schema
validation claim.

The guard costs only what it should: on the two coherent projects it reaches the
full union (81/81, 59/59), and it gives up ground only on CM4AI — 70 rather than
73 — dropping precisely the three asymmetric fields that made the unguarded
record incoherent.

## Historical result to re-evaluate

The original investigation reported a coverage gain of +1 to +4 slots and a mean
fitness gain of +0.023 to +0.042 across the four guarded merges. It attributed
most of the benefit to selecting among values in shared fields, rather than to
additional coverage. The table above preserves those reported measurements.

Those July scores are not evidence of a benefit on current arms. The current CLI
can select from saved judgments with a checked, pinned instrument using
`--fitness-context` and `--fitness-cache`; it does not generate fresh judgments
on a cache miss. Establishing current-arm benefit and feeding measured failure
classes into generation rules are separate obligations in #4765, following #2929.
